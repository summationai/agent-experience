# Decisions

Every non-obvious judgment call made while building AXE v0, with the reasoning. Entries are grouped by area and dated. When a decision is revisited, the original entry is edited in place and the change is noted, so this file reads as the current state of the design rather than as a changelog.

If you disagree with something here, open an issue that quotes the entry. Most of these are reversible before 1.0.

## Repository and tooling

**The project was built in an `axe/` folder of a larger monorepo and then moved to its own repository, `summationai/agent-experience`.** It was self-contained from the start (its own `package.json`, lockfile, CI workflow, and lint configuration), so the move was a history-preserving extraction of that subtree with `axe/` as the new root and no code changes beyond repository URLs. The fresh-clone verification script handles both layouts: it archives the current `git` subtree when the project sits in a subdirectory and the whole repository otherwise.

**pnpm 10 via corepack, TypeScript 5.9, Vitest 4, tsup 8, Turborepo 2.** TypeScript 7 (the native port) was available but the tsup, typedoc, and typescript-eslint chain still pins `< 6.1`, so 5.9 is the version that works everywhere without surprises. Vitest 4 is the latest line with a stable Node 20 story.

**Zod 4, and no `zod-to-json-schema`.** Zod 4 ships `z.toJSONSchema()` natively, targeting draft 2020-12, which is exactly the dialect the protocol specifies. `@axe/core` therefore has exactly one runtime dependency. The brief allowed `zod-to-json-schema`; not needing it is better.

**Node 20 as the floor.** Everything the SDK needs from the platform exists in Node 20: global `Request`, `Response`, `fetch`, `crypto.subtle`, `util.parseArgs`. `@types/node` is pinned to the 20 line so nothing newer leaks into the public API. The CLI uses `tsx` to load an integrator's `axe.ts`, because Node 20 cannot strip types itself.

**No argument-parsing or prompt library in the CLI.** `node:util.parseArgs` and `node:readline` cover every command. One fewer dependency in the tool integrators run in CI.

**ESM-first, CJS emitted by tsup for every package.** Next, Express, and older Jest setups still load CJS. Each package publishes `exports` with `import` and `require` conditions and separate `.d.ts`/`.d.cts` files.

## Vocabulary and drift prevention

**`spec/VOCABULARY.md` is the single source; `packages/core/src/vocabulary.ts` is generated from it.** The table has five columns: category, key, name, where it appears, meaning. A script (`scripts/gen-vocabulary.mjs`) parses the table and emits a frozen nested object `WIRE.<category>.<key>`. A test regenerates and diffs, so a hand edit to the TypeScript file fails CI. Markdown was chosen as the source because the spec is what reviewers read; the code is derived.

**`WIRE` is nested by category, not a flat list of constants.** `WIRE.path.manifest`, `WIRE.header.protocol`, `WIRE.status.needsInput`, `WIRE.field.continuationToken`. Flat `WIRE.FIELD_CONTINUATION_TOKEN` was considered and rejected as harder to read at call sites.

**Field names are enforced through TypeScript types, not `WIRE.field.*` at every property access.** Writing `envelope[WIRE.field.continuationToken]` everywhere would make the code unreadable and would defeat type narrowing. Instead, the drift test loads every package's `.d.ts` and asserts each vocabulary field appears as a property with exactly that spelling. Paths, headers, statuses, error codes, ladder values, kind names, MCP tool names, and CLI command names are used only through `WIRE`, and a source-scan test fails on any string literal in `packages/*/src` that starts with `/axe/`, `/.well-known/axe`, `AXE-`, or `axe_` outside the generated vocabulary file.

**The drift test scans inline code spans, not fenced blocks.** Fenced TypeScript is typechecked from `docs/examples`, which is a stronger guarantee than pattern matching. Fenced JSON blocks contain example data (`rentUsd`, `bedrooms`) that is legitimately not vocabulary. Inline spans are where prose refers to a wire name, and that is where spelling drift happens.

**Dotted kebab-case names are treated as wire names only when the namespace is a well-known kind namespace (`payment.`, `identity.`, `document.`, `contact.`, `consent.`) or the custom-kind prefix `x-`.** Action names such as `units.search` are integrator-chosen examples, not protocol vocabulary, and would otherwise force a long allowlist.

**SDK API identifiers are in the vocabulary too, under the `api` category.** `createAXE`, `register`, `fetchHandler`, `needsInput`, `handoff`, `resolveDisplay`, and so on are camelCase and would be flagged by the drift test's camelCase rule. Rather than allowlist them, they are vocabulary: the docs must spell them the way the `.d.ts` files do. This is consistent with the goal of the test, which is that no reader is ever told a name that does not exist.

## Protocol

**Error details are nested: `{ status: "error", error: { code, message, retryable, details } }`.** The brief describes the error case as "structured `{ code, message, retryable, details }`" and the human case as `{ handoff: {...} }`. Nesting both keeps the envelope's top level to `status` plus one status-specific member, which is easier to narrow in every language.

**`pending` was added to the event `ladder` enum.** The brief's list omitted it. Without it a long-running action has no event, and the analytics funnel would show those calls as missing rather than as in-flight.

**`payment.wire-instructions` from the brief became `payment.wire-confirmation`.** Well-known kinds name what the agent _submits_. For a wire transfer the site supplies instructions in `accepts[].instructions` and the agent submits a confirmation (reference number, amount, date). The brief's own worked example already used `payment.wire-confirmation`; this resolves the inconsistency in favor of the example.

**Tokens are HMAC-SHA256 signed and the server keeps state; the wire token carries no state.** Format: `base64url(header).base64url(payload).base64url(signature)`, where payload holds the token type, a random id, the action name, a hash of the originating input, the `onBehalfOf` identity if any, and expiry. Server-side `state` is stored in a `TokenStore` keyed by id. Encrypting state into the token was considered and rejected: it makes tokens large, leaks size information about state, and makes "single use" impossible without a store anyway.

**Tokens are single-use, and a repeat of the one use is answered, not refused.** A `needs_input` that offers three alternatives should not require three separate tokens, but a token that has been _consumed by a successful continue_ must not run again. A `continue` that fails validation or returns `error` does not consume the token, so the agent can fix the payload and retry. Revised 2026-09-24: a second presentation used to be `conflict`, which left an agent whose response was lost unable to learn whether its deposit went through. It now returns the stored envelope when the kind and payload are identical and `conflict` otherwise ([P-REQ-9], [P-HAND-6]). Consumption moved from a flag on the token record to an atomic claim in the idempotency store, because a read-then-write flag let two simultaneous continues both run.

**Idempotency keys are scoped to `(tenant, action, principal, idempotencyKey)`.** Two users, or two partners, sharing a key must not collide. A replay with a different input hash returns a `conflict` error rather than the cached result, because silently returning a result for different input is how double bookings hide. Revised 2026-09-24: the scope was the user, falling back to the site key id, which let a site key and a user whose id looked like it share a scope and left `true` verdicts with no scope at all; see the principal entry below.

**Default idempotency window is 24 hours; the store interface takes a TTL so integrators can change it.**

**One principal encoding for every scope (2026-09-24).** Tokens, idempotency keys, and operation claims are scoped to `site:<id>`, `user:<id>`, or both joined, with each id URI-encoded, so no user id can impersonate a site id. `site` actions include the user when `authenticate` also returns one; follow-ups must match exactly, including "none" for a token minted anonymously. The strictness is deliberate: allowing a signed-in caller to continue an anonymous token would run the follow-up as someone the original call was not. The login handoff is the one sanctioned transition, validated by the site's own server-side `completeHandoff`.

**A site key without an id is scoped by a keyed hash of the key (2026-09-24).** `verifySiteKey` may return `true`. Scoping all such keys together would give unrelated partners a shared replay scope; storing the key would put a credential in every token record. HMAC-SHA256 under the server `secret` distinguishes keys without storing them. The cost: rotating the key or the secret orphans the key's open tokens, which is what rotation should do. Sites that return an `id` avoid it.

**Every token refusal is the unknown-token `not_found` (2026-09-24).** Wrong tenant, wrong principal, revoked or narrowed site key: the response is byte-identical to an unknown token's, before any hook runs and before any stored result is read. `forbidden` for a narrowed key would confirm the token exists and name the action it belongs to.

**The idempotency store claims; it does not get and set (2026-09-24).** Atomic acquisition across instances cannot be built on `get` then `set`, and a process-local mutex would have fixed one instance while the docs promised many. The interface is `get`, `claim`, `complete`, `release`, with a lease for crashed holders, and there is no compatibility shim, because a shim over get/set would be the race under a new name. A concurrent request for a running operation gets a retryable `conflict` with `operationStatus: "in_progress"` rather than `pending`: `pending` needs a poll URL and a poll token, and the retry with the same key is already the poll. An error releases the claim instead of storing the error, matching the earlier rule that errors are not replayed. A claim is taken over only by the same fingerprint, so a crashed attempt can never be completed by a different request under its key.

**The SDK promises one run at a time and a replayed result, not exactly-once effects (2026-09-24).** Between a handler's commit and the stored result there is always a window. Rather than claim otherwise, handlers get `operationId`, stable across retries and instances, to make the effect idempotent downstream, and the docs show it in a transaction.

**`SqliteIdempotencyStore` is the reference adapter (2026-09-24).** It is executable in CI (on Node 22.5 or newer; the test skips on Node 20 with a message), every claim is one SQL statement that ports to PostgreSQL, and it lives in `@axe/core/node` taking a connection the caller opens, so `@axe/core` never imports `node:sqlite`. The Redis example uses Lua scripts and states its failover limit instead of presenting get/set as safe.

**Affordance target validation is two-phase.** Pointers into an action's own output schema are validated at `register()`. References to other actions are validated when the target is already registered, and any still-unresolved references are validated at finalization (first request or `describe()`). Requiring registration order would make large action sets painful to maintain.

**The `_axe` key is stripped from `output` and from every item before output validation and before display resolution reads dynamic affordances.** It may not appear in the declared output schema; registration rejects that.

**MCP tool names replace `.` with `_` and keep `-`.** `units.search` becomes `units_search`. `axe_continue` and `axe_resume` are reserved; an action whose derived name collides with a reserved name is rejected at MCP server creation with an error naming the action.

**Browser-sent writes are refused in the core, by content type and Origin, not by per-adapter middleware or CSRF tokens.** A cross-origin `text/plain` POST with a session cookie ran a mutating handler; CORS headers only decide whether the page reads the answer. The policy lives in `@axe/core` (`request-policy.ts`, called once at the entry of `handle()`) because every adapter ends in the same `handle()`, and a rule each adapter re-implemented would drift: the review found two adapters already relabeling parsed `text/plain` bodies as JSON, which would have defeated a content-type check done anywhere but on the original header. The adapters' only job is to pass headers through faithfully, and they now do. Origin checking was chosen over synchronizer tokens because the callers are agents and scripts as well as browsers: a token would need an extra round trip and a place to keep it that bearer clients do not have, while `Origin` and `Sec-Fetch-Site` are sent by every current browser on exactly the requests at risk and absent from server-to-server calls, which therefore pass untouched. The site's origin comes from `baseUrl` because `Host` and `X-Forwarded-*` are set by the client or the nearest proxy; there is deliberately no option to trust them. The content-type rule is unconditional (it is what the spec already said requests carry, and conformance can check it against any server); the origin rule applies when a `Cookie` header is present, so a public site's cross-origin agents and bearer callers are unaffected, and credentialed-CORS origins are trusted because they could already send the preflighted request. Not solved: ambient credentials other than cookies (HTTP authentication, client certificates) need `originCheck: "always"`; a browser that sends neither `Origin` nor `Sec-Fetch-Site` is treated as a server; side effects in `GET` handlers are the site's to avoid; and a proxy that strips `Origin` weakens the rule, which is why `SameSite` cookies are still recommended as a second layer.

**`policies.agents` uses exact vendor string match, case-insensitive.** Wildcards were considered and deferred; a vendor list in v0 is short.

## Presentation

**`display` is validated against the JSON Schema, not against the Zod type.** Pointers are resolved by walking `properties`, `items`, `$ref`/`$defs`, `anyOf`/`oneOf`/`allOf`. Walking the Zod internals would tie the SDK to Zod's private API.

**`toHTML()` emits no inline script from site data and no event handlers as attributes.** One static `<script>` block, authored in the SDK and identical for every render, attaches click handlers that read `data-*` attributes and dispatch `axe:select`. Every string from the site is HTML-escaped; every URL is validated to be `https:` or `http:` before being emitted as an `href` or `src`.

## Analytics

**Events carry no PII and no payloads by construction.** The event type has no field for input, output, or payload. `onBehalfOf` is not on the event. `agent` is the self-identification the agent sent, which is not the end user.

**The OpenTelemetry sink is structurally typed.** It accepts any object with a `createCounter`/`createHistogram` meter shape and an optional tracer, so `@axe/core` has no dependency on `@opentelemetry/api`. The doc shows passing the real API objects.

## Audit

**Weights live in one JSON file (`packages/testing/src/audit/weights.json`).** Categories: Discoverable 20, Describable 25, Presentable 15, Actionable 20, Trustworthy 20. Each check has a weight within its category; the category score is the weighted fraction passed, scaled to the category total. Agent-directed imperatives are a hard failure that zeroes the Trustworthy category regardless of other checks, because a manifest that tries to steer the agent is not trustworthy no matter how well it does elsewhere.

**A skipped check earns nothing, and a category with nothing scored is left out (review 2026-09-24, item 18).** The first scorer excluded skipped checks from the denominator, which was right, but gave a category whose checks all skipped its full maximum, so a URL that served no manifest scored 80, the floor this repository's CI uses. Two-part checks also credited an unrun half. Alternatives: count a skip as a failure (punishes a site for features it does not use, such as deprecations), or keep the maximum for an empty category (credits what was never observed). The chosen rule scores only what ran: an empty category is marked not scored and the total is scaled to 100 over the others. For the usual case, where every category has at least one check, the total is unchanged. Checks that passed because there was nothing to judge (no `needs_human` observed, no actions) now skip for the same reason.

**The reports say what a score is not.** A number next to the word "Trustworthy" invites reading it as a safety rating. Both audit reports end with the counted and skipped checks and a plain statement: the honesty checks are pattern matches, parity is a sample, and a score is not a security review or evidence of task success, adoption, or value. The conformance table says a skipped check was not verified. The words cost a few lines of output; the misreading they prevent is the one a reviewer made.

**Cloaking is not scored, only surfaced.** The audit cannot prove parity without a browser and a semantic diff of the human page. It prints the URLs to compare and, with `--browser`, fetches them and looks for the price and availability strings from the agent response in the human page. A miss is reported as a warning, not a score deduction, because false positives on dynamic pages would teach teams to ignore the section.

## Positioning (review 2026-09-24, item 18)

**The SDK is positioned as consistent human and agent behavior over one application's logic, not as a protocol to adopt.** The original framing (agents as the front door to every website; publish a manifest and agents will find you) rested on agent adoption of AXE discovery, which nothing in this repository shows and which a site cannot cause by publishing. What the SDK does deliver without that adoption: typed actions with explicit permissions, availability with reasons, one result shape, bound approvals, recoverable operations, and adapters that carry them into MCP, WebMCP, and the DOM. So the README, `docs/why-axe.md`, the concepts intro, the FAQ, and the landing page lead with that, and describe AXE as the HTTP representation underneath: useful, complete, and optional. No protocol feature was removed. Payment and identity kinds are described as payload shapes, because a validating payload is not an accepted payment and no wallet is known to produce them.

**Who benefits first is stated as a hypothesis.** Teams building interactive business applications, planning tools, and administrative workflows where people and agents share work look like the best first users, and evaluation, operational visibility, and safe execution may matter to them more than the wire format. No pilot has run. The roadmap labels each priority as an open SDK primitive or a commercial hypothesis so the two cannot be confused, and lists what this repository will not build (a hosted registry, billing, an identity provider, a payment platform, hosted analytics).

**Humor stays in the name and the tagline only.** The repositioning keeps both unchanged and adds none elsewhere; the prose around them is plain.

## Implementation (added during the build)

**`@axe/core/types` is a zod-free subpath.** The wire types live in `types.ts` with no runtime imports so that `@axe/client` and `@axe/mcp` can import them without pulling Zod into an agent's bundle. `@axe/core/display`, `/vocabulary`, and `/lint` are likewise zod-free.

**Generated vocabulary exports one frozen object per category, plus `WIRE`.** Agent-side packages `import * as WIRE from "@axe/core/vocabulary"` so bundlers drop the categories they do not use (`field` and `api` are the large ones and are only needed for docs tooling). Server-side code uses `import { WIRE }`. Both read as `WIRE.status.ok`. All `Object.freeze` calls carry `@__PURE__` so tree-shaking works. This is what keeps `@axe/client` under 15 kB.

**Stored `accepts[]` schemas are JSON Schema, and `/axe/continue` validates with the SDK's own validator.** A pluggable `TokenStore` (Redis, KV) can only hold JSON, so Zod schemas cannot travel with the token record. The wire form is JSON Schema anyway, so the server converts once at `needs_input` time and validates the payload against the stored JSON Schema on continue. The same validator runs in the conformance suite and the audit, which never hold Zod schemas. Consequence: Zod refinements (`.refine()`) on a kind schema are not enforced on continue; document the JSON-Schema-expressible subset as the contract.

**`_axe` stays on the wire; validation uses a stripped copy.** Agents need dynamic affordances, so the runtime validates the output with `_axe` removed and then sends the original output unchanged.

**Mutating actions require an idempotency key by default (`requireIdempotencyKey: true`).** The brief's fifth principle says mutating actions require idempotency keys. A curl user hits this immediately, and the error message says exactly what to add. Sites can turn it off; the conformance suite then warns instead of failing.

**Idempotency key presence is checked before the login handoff.** Otherwise an anonymous agent would receive a `login_required` handoff, send the human to log in, and only then learn its request was malformed. The key is stored with the login record and reused when the action re-runs after sign-in.

**Login handoffs are gated on `completeHandoff`; site handoffs are not, unless they ask.** The runtime's own `login_required` handoff cannot know whether the human signed in without the site telling it, so resume returns `conflict` with `handoffStatus: "open"` until the login page calls `completeHandoff(id, { onBehalfOf })`. A site-authored handoff resumes straight into `onResume` by default, because the site's own code can check the real-world state; `requireCompletion: true` opts into the same gate.

**Handoff ids are the token id, passed as `axe_handoff` in the URL.** The human's browser sees the id, never the signed resume token. Knowing the id lets a page call `completeHandoff`, which is a server-side call the site controls, and nothing else.

**Continue and resume re-establish identity and compare it with the token's binding.** A token minted for user A presented with user B's credentials, or anonymously, is `not_found`, not `forbidden`, so the response does not confirm that the token exists.

**`@axe/mcp` uses the low-level `Server` from the MCP SDK, not `McpServer.registerTool`.** `registerTool` takes Zod schemas; a remote manifest gives JSON Schema. The low-level `tools/list` handler accepts JSON Schema directly. Tool arguments are validated with the SDK's own JSON Schema validator before the action is invoked, so the model gets the same `invalid_input` shape either way.

**MCP tool calls poll `pending` results for up to 20 seconds before returning.** Most models handle one tool result better than a poll loop. Past the budget the result says to call `axe_poll`.

**The CLI loads `axe.ts` with `tsx`'s programmatic API.** Node 20 cannot strip types. `tsx` is the one dependency the CLI carries beyond the workspace packages; `node:util.parseArgs` and `node:readline` cover argument parsing and prompts.

**The CLI is ESM-only.** It uses `import.meta` and `tsx/esm/api`; nobody `require()`s a CLI.

**`axe conformance` calls mutating actions.** It is meant to run against staging: it invokes each mutating action's example, replays it, and exercises continue, resume, and tamper checks. `--no-mutate` skips those, and a `policies.agents` deny for the conformance vendor forces the same.

**Audit weights: hard failures zero their category, and the fix list is sorted by recoverable points.** A team should be able to read the top three fixes and know what to do this afternoon.

**The audit's cloaking section fetches `display.item.url` and looks for the agent-facing values as text.** This is a spot-check, reported as `✓` or `?` per value, never a deduction. Pages render numbers in many formats; a false accusation would teach teams to ignore the section.

**Screenshots of `toHTML()` are generated by `scripts/render-previews.mjs` with Playwright against the apartments example.** They are committed so the docs render on GitHub without a build step, and regenerated whenever the renderer changes.

**API reference is generated into `docs/api/reference/` so the hand-written `docs/api/README.md` survives regeneration.** TypeDoc's `cleanOutputDir` would otherwise delete the orientation page. The Zod re-export is marked `@hidden` so the reference does not include all of Zod.

**The drift test scans inline code spans in `spec/`, `docs/` (excluding `docs/api/`), and the README.** Example action names (`units.search`) and custom kinds (`x-oakridge.…`) are exempt by classification, not by allowlist. Dotted paths such as `policies.rateLimit` are checked segment by segment for camelCase segments only.

**Drift classification details.** snake_case tokens are only an error when they are within edit distance 2 of a vocabulary status, error code, ladder value, reason, or query name (`need_input`, `not_founds`), because site-specific reason codes and example ids (`u_204`) are legitimate. camelCase tokens are strict. Kind payload field names are vocabulary (`payload` category) because they are wire names agents must spell exactly. Enumeration members count as "used in source" when the whole enumeration is consumed (`z.enum(Object.values(WIRE.risk))`).

**Handlers receive `identity` and `siteKey`, and tokens are scoped to the acting principal.** Documentation review found that `Identity.claims` and the `id` returned by `verifySiteKey` were declared but never reached handlers. Both now arrive on every handler context. When a `site` call carries no user identity, the key's `id` (as `site:<id>`) scopes idempotency keys and tokens so two partners reusing the same `idempotencyKey` never collide; `context.onBehalfOf` remains the end user only.

**Runtime agent-read text is checked for agent-directed instructions.** Registration already rejects them in static text; text built at runtime (`message`, `instructions`, `whatAgentShouldSayToUser`, `accepts[].description`) is checked when the result is materialized. A match becomes an `internal` error and an `onError` report, so a site bug never reaches an agent as an instruction.

**`document.base64` payloads are capped at 10 MiB decoded, enforced on `/axe/continue`.** The spec said so; the code now does. Larger documents use `document.url`.

**Prettier does not format `docs/**/*.md` or the README.** It reformatted included code blocks (and turned fences into four backticks), which made every include stale. The include script owns those blocks.

## Site

**The site is a build output of the docs, not a second copy of them.** `site/build.mjs` renders `docs/**`, `spec/*.md`, and the root Markdown files with one template; the landing page pulls code from `docs/examples/` and prose from `docs/why-axe.md` through include markers, the docs hub and sidebar come from the ordered list in `docs/README.md`, and the demo data is produced by running `docs/examples/apartments/site.ts` in-process. Changing a sentence on the landing page means changing the doc it comes from.

**`site/dist/` is committed.** The deliverable is a directory someone double-clicks. Reproducibility is a test: two builds must hash identically, and the committed output must match a fresh build. The clock and `crypto.randomUUID` are pinned while the fixtures run so tokens, ids, and expiry timestamps are the same on every build; the audit report's timestamp is replaced with a fixed phrase.

**The Open Graph image is the one non-reproducible byte sequence.** It is rendered by a browser, and text rasterization differs across machines. It is excluded from the reproducibility hash and from the CI freshness diff. Rendering it deterministically would require bundling a font and a pure rasterizer, which is more machinery than one social card justifies.

**Mermaid is rendered with `beautiful-mermaid`, a pure-JavaScript renderer.** It is synchronous, has no DOM dependency, and produces identical SVG on every machine, which the mermaid CLI (headless Chromium, system fonts) does not. Its Google Fonts `@import` is stripped so the SVG makes no network request; the diagram uses the system font stack through CSS variables so it inverts with the theme. Each diagram carries an ASCII rendering and its source behind a disclosure as the text alternative.

**Shiki runs at build time and emits classes, not inline styles.** Dual-theme inline styles cost about 45 bytes per token. Identical light/dark color pairs become short class names (`t0…tN`, assigned in a deterministic order) with the pairs emitted once as CSS custom properties; two rules switch between them for the theme. Consecutive same-style tokens are merged.

**The page script is inlined and minified; data loads on intent.** Lighthouse's simulated LCP counts every script the page requests, deferred or not, so an external `site.js` plus the demo data would have cost ten points. The script is inlined (one classic `<script>`, no module, works from `file://`); the ladder envelopes and the rendered search (`fixtures.js`) load when the demos come within 800 px of the viewport or are interacted with; the search index (`search-index.js`) loads when the search control is hovered, focused, or opened. Both are classic scripts injected by the page, never `fetch()`, so `file://` works. A reader who never scrolls never downloads them. The brief's "embedded as a `<script type="application/json">`" became a shared deferred data script for this reason; nothing is fetched.

**The stylesheet is one file with landing-only and docs-only regions.** Each page type inlines only the regions it needs plus the shared ones. Inline CSS removes a render-blocking request; region splitting keeps the inlined bytes down.

**The rendered search is a sandboxed `srcdoc` iframe.** It is the unmodified output of `toHTML()`, including the renderer's one static script. `sandbox="allow-scripts"` lets that script dispatch `axe:select`; the iframe posts the selection to the parent, which binds the unit id into the ladder demo. The only alternative that keeps the output unmodified is an iframe.

**Lighthouse runs against a local port with gzip, best of up to three runs.** Lighthouse does not audit `file://` URLs; the test serves `dist/` on a loopback port for the run only, compressed the way any static host would serve it, because Lighthouse's simulated network time is a function of transfer size. Simulated metrics vary run to run by a point or two, so the test takes the best of up to three runs, which is Lighthouse's own recommendation for stable scores. Both audited pages score 96 on performance and 96 to 97 on accessibility at the time of writing.

**Screenshot baselines are compared only on the platform that produced them.** Font rasterization differs between macOS and Linux; the baselines record their platform, and the comparison is skipped elsewhere rather than failing on noise. `--update-screenshots` regenerates them.

**TypeDoc output is rendered like any other Markdown, with unresolvable links unwrapped.** TypeDoc links to Node's types and to source lines; sources are disabled (they embedded a commit hash and pointed at the wrong repository), and links to symbols the reference does not contain become plain text so the link checker stays strict for everything else.

**Root README badges are dropped from the site.** They are images from shields.io; the site is offline-complete. The alt text is rendered instead.

**`llms.txt` is a curated integration guide, not a link dump, and `llms-full.txt` is generated.** The llms.txt convention asks for an index of links with one-line descriptions, and a link index is what the docs hub already is. The reader this file is for is an agent about to wire the SDK into an application it did not write, and what such an agent gets wrong is not which page to open but which shape to pick, which rule it is about to break, and how the packages reach its build. So the root `llms.txt` is hand-written around those decisions (the shape, the scars, packaging, flags, tests), keeps the convention's structure (an H1, a blockquote, H2 sections of `- [title](path): description` lines, an `## Optional` section), and states only what the repository can back with a path. The full-text file is not hand-written because the docs are the source and the site is their build output: `site/build.mjs` writes `site/dist/llms.txt` with links rewritten to the published pages and `site/dist/llms-full.txt` as the index followed by every doc and spec page in navigation order, and the site test fails when a link does not resolve or a page is missing, so the two files cannot drift from the docs the way a second copy would. The generated API reference is left out of the full file; the `.d.ts` files are the better source for a signature.

## Surface

**Surface is the inside-out half of the protocol, not a replacement for the manifest.** The sumapps trials (a browser-state draft board and a server-state planning grid) showed that hand-written actions beside a human UI drift, and that a static manifest cannot say what can be done right now. Surface generates the agent view from the same registrations the controls use. AXE keeps the outside-in half: discovery, the envelope, kinds, tokens, handoff. `@axe/surface/axe` joins them, so a surface is served as ordinary actions (one per control, plus `observe` and `ledger`) and every existing tool (MCP, conformance, audit, events) applies unchanged.

**`act` returns the AXE result envelope instead of Surface's own `{ ok, error, reason }` shape.** The port had four refusal strings (`stale`, `unknown-target`, `unavailable`, `invalid-op`). Each already had an AXE code: `conflict`, `not_found`, `unavailable` (as an `error` code), `invalid_input`. One envelope means one client, one presenter, one set of tests. `changed` and `rev` ride in `output` so a stale act is visibly a no-op.

**`effect` is AXE risk metadata.** `undoable` in the original is `reversible` here (the old name is accepted and deprecated); `risk` defaults to `medium` for anything that mutates, matching the manifest default. Each control's action declares its own effect's risk (revised with contract v0.3; the generic `<ns>.act` used to declare the highest of any registered effect), so an audit that reads the manifest sees the number the control itself carries.

**Unavailable controls can say what would unblock them.** Rule 1 (Surface reports, never decides) said nothing about what the agent should do with a reason string. `state.requires` names AXE kinds with an application-owned `fulfill`, and `state.handoff` names the human step. Through the bridge these are `needs_input` and `needs_human`; standalone they ride in `error.details`. This is the "more control to both sides" the integration asked for: the application says exactly what it needs, the agent can supply it without a human, and neither invents anything.

**The revision stays application-owned.** Browser-state apps `bump`; server-state apps `setRev` from the server's counter and keep their own stale check as the second gate. Surface never generates revisions from content hashes, because a hash cannot distinguish "changed and changed back" from "unchanged", and the ledger needs the former.

**The DOM mirror is a helper with a contract, not advice.** The first trial's largest gains against browser agents came from accessible names, and the port left producing them to the application, so [S-DOM-1] was a SHOULD that nothing enforced. `surfaceAttributes` now returns the set (`aria-label`, `data-surface-id`, `data-surface-kind`, `data-surface-object`, and `aria-disabled` or `aria-readonly` with `data-surface-reason`) and `useSurfaceProps` spreads it, so the name an agent reads on the page is the name `observe()` reports by construction rather than by discipline. Three choices in the set: `aria-label` rather than visible text, because a button's visible text is the widget ("Draft") and the name is the outcome ("Draft Jahmyr Gibbs (RB)"); `aria-disabled` rather than `disabled`, because the application keeps its own disabling logic (Rule 1) and an `aria-disabled` control stays focusable, so a screen reader reaches the reason beside it; and the reason mirrored into `data-surface-reason`, so a browser agent that never calls `observe()` still learns why not before it clicks. `describeEntry` is not rendered by default: one line per control as `aria-description` is noise on a dense grid, so the application opts in. `surfaceSelector` quotes and escapes the id rather than restricting ids, because the trials' ids carry colons and object keys.

**`useSurface` replaces in place; React is optional.** Unregister-then-register on every render reorders the table and moves an agent's index. The hook updates the existing entry when deps change and unregisters on unmount. `react` is an optional peer so server-only surfaces carry no React dependency.

**Two staging defects are rules, not fixes.** The first trial on a real planning grid found an act with a `null` target matching a disabled row, and a table that kept reporting cells editable while the application had frozen editing during a save. Each could have been patched in the application alone. They are rules of the contract instead ([S-ACT-6..8], [S-REV-5], [S-FRZ-1..4]) because both live in the seam, where the next application would meet them again: the surface now refuses any target that is not an id or a non-negative integer before it looks anything up, an index resolves only through the observation at the presented revision (so a row without an index is unreachable by number), and `freeze(reason)` exists so that "disabled while saving" is one call rather than a re-registration the application has to remember. `freeze` moves the revision on both ends when the surface owns it, since a freeze is a change an agent could observe; what it does under an application-owned revision is the subject of "The revision has a mode" below. The name is `freeze`/`thaw` rather than `suspend`/`resume` because `resume` already means something on the ladder.
**The ledger lives in the surface, and refusals are in it.** The first Surface left the record of who acted to the application ([S-REV-4] was a SHOULD), and its own critique of the integration was that the person never sees the agent's work: no ledger, no attribution, no replay. An application-side ledger records what the application chose to record, in its own shape, after the fact, and neither trial application had written one. The surface is the one place every act passes through with the actor, the revision the agent saw, and the revision the handler produced already in hand, so recording there is one append per act and the same shape for every application; `observe()` carrying `ledgerSeq` makes "what happened since I looked" one call. Refusals are recorded because they are half the story: an agent that observed at rev 7 and was refused at rev 9 did nothing, and the record has to say so rather than leave a gap that reads as nothing happened. A person reviewing the agent's work sees the attempts as well as the changes; an agent sees its own stale acts next to the human's moves that caused them. The ledger is bounded and in memory, the application's live record rather than its audit log; the action events the bridge emits feed whatever durable store the site already runs. Those events are a second channel in `@axe/core` (`onActionEvent`, `emit`) rather than a field on the analytics event, because [E-2] forbids the analytics stream from naming anyone and attribution is the whole point here.

**One AXE action per control, not a generic `act`.** The first seam served a surface as three actions: `observe`, a generic `act` taking `target` and `op`, and `ledger`. The reviewer who designed Surface had written that each available entry can be published as an AXE action, so discovery, MCP, kinds, and the audit come for free, and the generic action gave that up: an agent reading the manifest or an MCP tool list saw one `act` tool and had to call `observe` to learn what it could do, the manifest's `availability` could say nothing per control, and the audit scored one action's risk for a board of controls with different risks. Contract v0.3 publishes one action per entry (`board.pick-me-gibbs`, "Draft Jahmyr Gibbs (RB)"), with the entry's `effect` as its metadata and its live `state` as its `availability`, so `/axe/state` answers per control and the MCP tool list reads like the page. What it costs: the manifest changes shape whenever rows register or unregister, so it is a snapshot of the page rather than a description of a site, and it grows with the table (300 rows is a 300-action manifest, which validates and is what the agent needs to see). Two things keep the cost bounded: the set is rebuilt only when the registry changed shape (`registryVersion`), never on a `bump`, and `observe` stays as the one-call view with an affordance per row, so an agent that wants the whole table at once still has it. Entry ids are not valid action names, so the bridge maps them: a plain slug when it is free, a short hash suffix only on collision, and a sticky bidirectional map so a name never comes to mean a different control and a row that leaves and returns gets its name back ([S-AXE-7]). The generic `act` was removed rather than deprecated because the package is unreleased.

**Dynamic actions in the server are a provider hook, not unregister and replace.** Two mechanisms were considered for a set of actions that changes while the server runs. `axe.unregister(name)` plus `axe.replace(action)` would let a bridge sync the server on every change, but Surface's `register` does not notify (only `bump` does), so the bridge would either sync on every request anyway or miss a row registered without a bump; and it would put a mutable registry behind an API whose invariants (unique names, lint at definition, idempotency keyed by name) were designed around append-only registration. An `ActionProvider` (`actions()`, `get(name)`, `onChange`) consulted after the registered actions whenever the server enumerates or looks up by name keeps those invariants where they are: every provided action is still built with `action()` and linted there, names are checked for uniqueness when the set is enumerated, auth modes are checked once per action object, and the idempotency store is untouched because it never depended on the action existing. `get(name)` exists so that invocation on a large set is a map lookup, not a scan; `onChange` exists so the derived MCP server can send `notifications/tools/list_changed` instead of being asked to poll. One consequence surfaced in the tests and became server behavior: an action's own last invocation may remove it (a pick that leaves the board when drafted), so a retried `idempotencyKey` for a name that no longer resolves is answered from the idempotency store before `not_found`, as [P-IDEM-2] already requires for the same attempt.

**`@axe/core/node` is a subpath, and the surface never imports Zod.** The first real integration bundled the surface for the browser with esbuild and failed on `fs/promises`: `jsonlFileSink` reached for it through a dynamic import, and a bundler resolves specifiers before it tree-shakes, so a browser bundle that would never call the sink still could not be built. The application aliased the built-in to an empty module. A conditional import (`typeof process`) or a `browser` field would have hidden the same problem behind more configuration; a subpath that is the one place in the package that needs Node is simpler and honest, and the export list of `@axe/core` no longer promises something a browser cannot run. Dropping the re-export from `@axe/core` rather than deprecating it is deliberate: a re-export is an import, and the import was the defect. The same bundle carried all of Zod for a surface that never used a schema, because `@axe/surface` imported `isZodSchema`, `toJsonSchema`, and `validateJsonSchema` from entries whose module-level schema definitions cannot be shaken away. The surface now imports only `@axe/core/vocabulary` and the new zod-free `@axe/core/json-schema`, detects a Zod schema by the shape of `safeParse`, validates by calling it, and asks the application for the converter (`createSurface({ toJsonSchema })`) when a Zod schema has to be published. The application that registers Zod schemas already has Zod, so passing the converter costs it one import; every other application gets a 21 kB bundle. `register` throws when a Zod schema arrives without a converter rather than publishing an empty schema, because an `accepts` entry with no schema would be a lie in the manifest. A bundle test keeps it so, since this is exactly the kind of regression a unit test never sees.

**The revision has a mode.** `freeze` and `thaw` moved the revision, which is right when the surface owns the counter and wrong when the application adopts a server's: the surface's counter drifted one or two ahead of the server's until the next `setRev`, and an agent that observed in between was refused for a change that never happened. The application pinned the revision back after every freeze. The surface now knows who owns the revision: `bump` says the surface does, `setRev` says the application does, the last call wins, and `createSurface({ revision })` pins it for applications that want no inference. In `app` mode a freeze is reported (on every entry, in `observe().frozen`, and to `onChange` listeners) and moves nothing, because a freeze is not a change of the application's state; an act planned before the freeze is `unavailable` while frozen and accepted afterwards exactly when the application's revision did not move, which is the truth the application can vouch for. Inference from the last call was chosen over a required option because every existing application already makes exactly one of the two calls, and over a hash of behavior because the mode has to be stable while a freeze is held. `registryVersion` does not move on a freeze in either mode: it means "the table changed shape", the bridge rebuilds its action set on it, and availability is live without a rebuild.

**A handler reports what it did.** With a server revision the handler is asynchronous and the revision arrives later, so every `ok` carried `changed: []` and the ledger recorded `revBefore` equal to `revAfter`: the record was true and useless. The handler is the one place that knows both what changed and, when the server answers, the revision it assigned, so it may return `{ changed, rev }` and the surface folds both in. A return value was chosen over a second `setRev` from inside the handler because the surface has to adopt the revision after the handler and before the result, in one place, with the ledger written last; and over a callback argument because handlers are the application's existing functions, which a return value leaves alone. Inference stays for the browser case: a handler that bumps and returns nothing still gets `changed: [id]`. The spec says plainly that in `app` mode `changed` is what the handler reports and agents should re-observe, rather than pretending the surface can know.

**The DOM mirror is an instance method with a remove list.** `surfaceAttributes(entry)` read the entry's own `state` and `edit`, so during a freeze the page said editable while `observe()` said frozen, and it returned only attributes to set, so a cell that became editable again kept the previous render's reason. The application folded `availability(id)` in and deleted the state attributes by hand. `attributesFor(id)` does both on the surface, because the surface is the only thing that knows the live availability, and `remove` lists every canonical attribute not in `set` rather than the three state attributes, so a renamed or added attribute in the vocabulary never leaves a stale value behind. `surfaceAttributes` stays for a one-time render and for observed rows, which carry their state with them; the doc says which to use when. `useSurfaceProps` subscribes to `onChange` and re-renders on a change of its own attributes only, so a table of hundreds of rows pays a string comparison per row per change, not a render.

**A collection that cannot load more is not an action.** The bridge published one, always unavailable ("cannot load more"), because [S-AXE-6] said every entry is an action. An action that can never run is noise in the manifest, `/axe/state`, and the MCP tool list, and the entry already has a row in `observe` where `total`, `loaded`, `filter`, and `sort` are what an agent wants from it. The row stays; the action goes.

**The ledger is complete rather than the manifest bounded.** Over-length text was refused by the entry action's input schema at the protocol layer, before the surface ran, so the attempt was neither ledgered nor emitted as a `surface.act` event. Two fixes were possible: keep the tight schema and document the gap, or loosen the bridge's input to the shape (`text` a string, `confirm` a boolean) and let the surface refuse. The ledger exists so the person sees the agent's attempts, and a refusal that never reaches it is the gap the ledger was built to close, so the second. What is lost: `maxLength` and the field's schema no longer appear in the entry action's input schema, where an agent could have validated before sending. They still appear in the input's description, in the action's description, and in `observe()` as `edit.maxLength` and `edit.schema`, and the agent's experience of a refusal is the same `invalid_input` at `/text`. A malformed request the protocol refuses before the surface (a number for `text`, a stale `expectedRev`) is still in the server's request events; the spec now says so.

**A handoff without a `url` is reported, never resumed.** The application had a human-only step with no page to point at (unlock a version from a menu) and could only report a bare reason, because `HandoffSpec.url` was required and inventing a URL would have been a lie the bridge would then mint a resume token for. `url` is now optional on a declared handoff, in Surface and in the protocol's availability ([P-LIVE-5]), and the ladder is unchanged: `needs_human` still requires a complete Handoff ([P-HAND-1]), because a resume needs a page the person came back from, so the bridge climbs to `needs_human` only when the handoff has a `url` and otherwise stays `error` `unavailable` with `details.handoff`, where the agent still finds the `instructions` and `whatAgentShouldSayToUser`. The alternative, a separate field for an in-application step, would have been a second shape for the same idea.

**`auth` defaults to public.** `createAXE` required `auth` and, when it was missing, complained that `auth.modes` had a bad value. Most first integrations are public read-only surfaces, `{ modes: ["none"] }` is what every one of them wrote, and a default of "no credentials" cannot grant anything: an action that declares `auth: "user"` still fails registration until the mode is declared. An explicit empty `modes` remains an error, with a message that says to omit `auth`.

**The bridge's actions default to `user`, which a public server refuses.** The public default for `createAXE` was right for hand-written actions, whose author sets `auth` per action, and wrong for the bridge, which generated every action with the action builder's default `none`: a server configured with `none` and `user` still served `observe` (every field value), the ledger (every typed text), and every mutation to an anonymous caller. The bridge now declares its own mode, `user` unless the options say otherwise. We considered deriving the default from the server's modes (`user` when the server has it, else required), but the provider cannot see the server's configuration when it is created, and a default that silently became `none` on a public server is the defect itself. Declaring `user` and letting the runtime's existing [P-AUTH-1] check refuse it gives the rule in one sentence: a surface is served publicly only when someone wrote `auth: "none"`. The cost is one line for a test harness or a demo, which we accept.

**One surface per caller comes from a template, not a union.** The runtime's `ActionProvider` has no caller: `actions()` and `get(name)` answer for everyone, and only handlers and availability hooks see the identity. So the action set cannot follow each caller's entries. A union of every caller's entries would publish one caller's row names to all the others and to anonymous readers, so the set is a fixed template the application registers (its shape, named without anyone's data), and each request resolves the caller's surface for state, values, and handlers. Rows outside the template stay visible in the caller's `observe` without an action. The resolver is the application's (`(context) => Surface | null`); `scopedSurfaces` is the common case with a bounded, idle-evicting cache, keyed by tenant and principal rather than by the actor string an application may rename.

**An unidentified caller's availability is `{ available: true }`, not a reason.** The manifest's availability is computed for nobody, and `/axe/state` for whoever asks. Reading a protected surface there would publish its reasons ("already drafted by Dana Reyes") to anyone. Reporting `{ available: false, reason: "sign in" }` would put an authorization message in a capability report and stop an agent from trying the call that yields the login handoff. The protocol already reports `{ available: true }` for an action that declares no availability; for a protected entry and an unidentified caller the bridge makes that same non-claim, and `auth` on the action says who may call.

**Sensitive is a field flag and the ledger has a text policy.** A field's value and the text typed into it are the two places a surface holds user data it did not render as a name. `sensitive: true` removes both everywhere the surface writes them, including refusals, and an unresolved target is treated as sensitive while any sensitive entry exists, because a refusal before resolution cannot say which row it meant. The `hash` policy is a synchronous SHA-256 in the surface (Web Crypto is asynchronous and the ledger is written in-line); it links equal texts and is documented as not hiding guessable ones.

**Consuming from a checkout is a script and a doc, not a bundle.** `pnpm pack` rewrites `workspace:*` to the packed version, so a consumer needs an override per packed sibling, and `@axe/testing` pulls `@axe/client`. The first consumer wrote its own vendoring script and learned each of these by failing a Docker build. `scripts/pack-for-consumer.sh` and "Consume from a checkout" in `docs/deploying.md` say it once, in general terms. Bundling `@axe/client` into `@axe/testing` to save one override was considered and rejected: it would ship two copies of the client to anyone who uses both, for a problem that ends when the packages are published.

**The fantasy-draft and planning apps were not vendored.** They are Summation products with their own backends. The board fixture in `packages/surface/test` mirrors the draft board's row registration exactly (three players, drafting on and off, roster slots, undo), so the two-actor rules are tested against the shape they came from; `sumapps` can switch its import to `@axe/surface` and delete its copy.

**A revision check before the handler is not concurrency control; the surface orders its acts and the write is the second gate.** A review ran two asynchronous acts with the same `expectedRev` against one surface: both passed the comparison, both ran, both returned `ok`, and the ledger recorded both at `revBefore: 0`. The `app` revision mode did not help, because the comparison still ran before a handler that awaited. Two designs were considered. A revision reservation alone (refuse any second act presenting a revision already claimed) needs a notion of "released", and in `app` mode the revision may not move until the server's answer is adopted, so a reservation would either deadlock the next observation or expire on a guess. A per-surface queue orders the acts and lets the second be checked against the first one's result, which is what the contract means by "an act whose revision has moved applies nothing". The queue was chosen, with every pre-handler check run at the call as well, so a refusal (stale, frozen, unknown target) never waits behind a slow handler, and an idle surface still starts its handler within the call, which the freeze-during-save behavior depends on. One piece of the reservation idea stayed ([S-ACT-10]): a commit that leaves an app-owned revision where it was (the handler reports no `rev`) closes the claims taken before it at that revision, because the surface cannot tell whether it changed what they were planned on; a claim taken after it is accepted, so an agent that observes again is never stuck on a revision that cannot move yet. Reads do not wait, since an observation is a snapshot at a revision and a handler in flight has not committed.

The queue guards one surface. Two tabs of the planning application are two surfaces, and no browser-side mechanism orders their writes on the server. So the handler gets the presented revision (`ActContext`, a third argument rather than a changed signature, so existing handlers are untouched) and a typed way to say its conditional write failed: a thrown `SurfaceConflict` or `{ conflict }` in the report. Both were kept because a handler that already throws on a failed write can keep throwing, and one that returns a result object can say it in the result. The surface does not adopt the `currentRev` a conflict reports: a refusal is not a change, and the application's revision reaches the surface through `setRev` on its next refresh, the one path that already carries it with the rest of the state. A handler's late `rev` lower than the surface's is ignored and ledgered as `ignoredRev` rather than refusing the act, because the write did commit and a refusal would report a change as nothing; within one surface such a report can only come from a change outside `act`, since acts cannot complete out of order.

**No per-entry revisions.** Resource-scoped preconditions (a revision per entry, so acts on unrelated cells do not conflict) were considered and left out. No trial showed a need: in the planning application a conflict on an unrelated cell costs one re-observation, and the server's conditional write can be as narrow as its own data model already is (per branch, per row) without the surface knowing. If a need appears it would be an optional, additive field on the entry and the act, never a change of meaning for the one revision, which agents and the protocol's stale check already rely on.

**The React hooks own an (id, target) pair and call the latest handler; store readers get `subscribe`, not a louder `onChange`.** Mounted tests (review item 11) showed `useSurface` keyed its effect on the caller's `deps` alone and remembered the first id in a ref, so an id change left the old row registered, a target change registered nothing, and a handler read the render that last changed `deps`. Adding every closure to `deps` would re-register on each render, since callers write handlers inline. The hook now registers a copy of the entry whose functions delegate to a ref holding the latest entry, keys the refresh on `[target, id, ...deps]`, and unregisters the previous pair in a separate effect keyed on `[target, id]`, so an ordinary refresh still replaces the row in place ([S-ENT-5]). `useSurfaceProps` also missed registrations made outside the component, because registration never notified. Making `onChange` fire on `register` was the obvious fix and the wrong one: the bridge forwards `onChange` (filtered by `registryVersion`) to the server's `onActionsChanged`, which sends MCP `tools/list_changed`, so an adapter that re-registers hundreds of rows per scan would send one notification per row. `subscribe` is a second, additive channel with the external-store shape: it fires on everything a reader could see, and `onChange` keeps its meaning. Registration moved to a layout effect so a control never paints with the previous registration's attributes. This is a contract change (a new rule, [S-OBS-4]), hence v0.6. The fixes to the hook alone would not have been one.

**Granularity is measured, and the seam has two (review 2026-09-24, item 16).** The entry "One AXE action per control, not a generic `act`" argued that a tool list should read like the page, that `/axe/state` should answer per control, and that the audit should score each control's own risk; it accepted that the manifest grows with the table ("300 rows is a 300-action manifest, which validates and is what the agent needs to see") and counted on the cached action set to bound the cost. The review pointed out that caching bounds the server's cost, not the agent's: the agent still reads every tool, pays for every `tools/list_changed`, and chooses among them. Measured on one application served both ways (`scripts/measure-granularity.mjs`, report in `docs/review/2026-09-24/data/granularity.md`; scripted, not model performance; tokens are bytes / 4):

The argument for one action per control holds where it was made, on a draft board of tens of controls: at 5 controls the two shapes cost the same, and a per-control list is the more legible one. It does not hold at 300 or 1000 controls, where the tool list alone is an estimated 100,000 to 340,000 tokens before the agent has done anything, or on a page that re-registers rows on every edit, where 46 of 50 ordinary changes each sent a `list_changed` (25 to 28 of them with no tool's description or schema changed). So `domainActions` joins `surfaceActions` instead of replacing it: a fixed set of parameterized actions, each covering a group the application declares (`covers`), taking the entry id, and running `surface.act` exactly as the entry's own action does, so the revision, the ladder, the ledger, and the events are identical and a test proves it by running one script both ways. The generic `act` of v0.2 is not back: that took any target with one maximal risk; a domain action covers a declared group whose risk, reversibility, and idempotency are checked against each member, and an entry that exceeds them is left uncovered and reported rather than published under a lower number. Availability per entry moves from the manifest to the `observe` rows and the act's refusal; the manifest keeps one availability per domain action (any covered entry actionable, else the shared reason or `idleReason`). `humanHandoff` is declared on the spec because it cannot be derived from entries that do not exist yet. Per control stays the default of `surfaceActions` and the recommendation for small surfaces; domain actions are the recommendation above a few dozen controls or when rows churn; both can be served side by side under different namespaces while agents move over. The per-control `list_changed` on re-registration without a tool change is left as measured: the in-process MCP bridge could compare tool fingerprints before notifying, as the remote path already does, at the cost of building the tool list on every change; that is a separate change.

**`<ns>.observe` pages, in both granularities.** A domain action is only as cheap as the read before it, and an unfiltered observation of 1000 rows is 361 KB. `<ns>.observe` now takes `object`, `kind`, `available`, `query`, `limit`, and `cursor`, declares the protocol's `pagination`, and returns `total` and `nextCursor`. Rows keep registration order and their whole-observation `index`, so a filtered page never renumbers the rows an index can reach. The per-control default page is 1000 rows, so an existing caller of a surface up to that size gets the same single page; the domain default is 50, at most 200. A cursor names the last row returned and the one after it rather than an offset, so a row that leaves between pages does not shift the next page; a cursor for other filters is refused. `surface.observe()` is untouched: local callers keep the whole table.

**The revision stays global; a per-entry precondition is a proposal, not code.** In a scripted two-actor run on a 300-control surface (400 trials per rate; a person makes a Poisson-distributed number of demand edits during the agent's think time, 10% of them on the agent's row), the share of the agent's first attempts refused as `conflict`, and the share of those caused only by edits on other rows, were:

| Person's edits per agent act (mean) | Conflict rate | Unrelated share of conflicts | ok within 3 attempts (filtered re-observe between) |
| ----------------------------------: | ------------: | ---------------------------: | -------------------------------------------------: |
|                                0.25 |         22.3% |                        83.1% |                                              99.0% |
|                                   1 |         63.0% |                        79.8% |                                              74.0% |
|                                   3 |         94.3% |                        61.0% |                                              14.2% |

The numbers are identical in both granularities, because granularity does not touch the revision. They show a real cost when a person and an agent edit the same large surface at once: most conflicts are about rows the agent never read, and at three edits per agent act retries rarely land. The design that would address it: an optional per-entry revision on each observed row (moved when that entry's reported value, state, or edit changed, or supplied by the application), and an act precondition on that entry revision presented in place of the global one, accepted when the entry's revision has not moved. It is not implemented, for three reasons. The protocol's stale check ([P-LIVE-3]) runs on the envelope's global `expectedRev` before any handler, so the precondition needs a protocol rule for a scoped revision, not a bridge option. "No shared state" is the application's knowledge, not the surface's ([S-RULE-1]): a row total or a derived cell makes two entries related, so the application would have to declare the dependency scope, and a wrong declaration silently applies an edit over a change the agent never saw. And the cheaper remedy already works at ordinary rates: with a filtered re-observe (one row, a few KB) and up to three attempts, 99% of acts land at a quarter of an edit per act. The proposal stays here with its measurements until an application shows the concurrent-editing rate that needs it.

## Live state

**Live state is optional and additive; the protocol stays `axe/0.1`.** A reviewer who trialled Surface on two applications put it plainly: the manifest is static and an action is a function, so "what can be done right now and why not the rest" was not expressible, and idempotency keys handle retries, not a person and an agent editing the same record at once. The fix is two optional members on documents that already exist (`rev` on every envelope, `expectedRev` on every request that may change state, `live` on the manifest, `availability` on an action) plus one optional endpoint. A site that publishes none of them serves byte-identical responses to before, and an agent that never sends `expectedRev` is never refused for it. [P-VER-4] (unknown fields are ignored) is what makes the addition safe within a minor version, so no version bump.

**One site-wide revision, not per-resource ETags.** ETags answer "has this one resource changed" and require the agent to know which resources an action touches; an action touches several, an agent observes a whole result at once, and the question it needs answered before acting is "has anything I saw moved". One opaque value answers it, matches what Surface already does (one revision per application), and costs a site one counter or one `updated_at` max. Revisions are compared for equality only, never ordered, so a site can use a counter, a timestamp, or a hash of its state without agents depending on the choice. Per-resource precision is available to a site that wants it by scoping its revision per tenant, and in future by a per-action `revision` hook if a need appears; none appeared in the trials.

**Per-action availability is a report, not a gate.** The runtime renders `availability` into the manifest and `/axe/state` and delivers the computed value to the handler, but it does not refuse the call itself. This follows Surface's first rule (Surface reports; it never decides) and keeps the handler as the one door: a site whose handler already climbs the ladder for the unavailable case (a `needs_input` with the declared `requires` as `accepts`) is not short-circuited into a bare `unavailable`, and authorization stays where the site put it. The obligation is on the wire instead: [P-LIVE-6] says an unavailable action must not return `ok`, the conformance suite calls one and checks, and the audit scores it. The `unavailable()` helper makes the honest refusal a one-liner and carries the same `reason`, `requires`, and `handoff` in `error.details` that the manifest showed, which is also the shape Surface's standalone `act` already emitted.

**The stale check runs after the idempotency replay and before the handler; expectedRev is not part of the idempotency binding.** An `idempotencyKey` means "this is the same attempt"; `expectedRev` means "this is the state I saw". A retried request with the same key and input is the same attempt and gets the stored envelope, whatever revision it carries, because refusing it would turn a lost response into a failure the agent cannot distinguish from a real conflict. A new key with an old revision is a new attempt on stale information and is refused, which is what stops a lost response from being double-applied with a fresh key. A stale request stores nothing under its key, so the agent may reuse the key after re-reading; error results were never stored, so this fell out of the existing rule. The check also runs before a login handoff is minted, so an anonymous agent with a stale view learns it immediately rather than after sending a human to sign in, and the revision is carried in the login record and re-checked when the action finally runs, because the action had not run yet and the agent's claim still stands. Continue and resume accept `expectedRev` with the same check, placed after token and payload validation so an invalid payload is reported first, and a stale continue leaves the token unconsumed like any other error.

**The manifest carries the anonymous view; `/axe/state` carries the live one.** Manifests are cacheable by rule ([P-DISC-3]) and shared across callers, so any `availability` in them is computed for an anonymous caller and `live.rev` is the revision at render time; both are labeled a snapshot in the spec. Availability may legitimately depend on who is asking (credits on a member's pass, a planner's approval), so the state endpoint establishes identity the way an action does, sends `Cache-Control: no-store` and `Vary: Authorization`, and lists every action so an agent never has to merge two documents. The manifest's `live.url` is absolute like every other URL in the manifest, and a site with a `revision` but no `availability` hooks still serves `/axe/state` so the revision can be read without calling an action.

**Surface adopts the protocol's stale shape.** Surface refused stale acts with `details: { rev, expectedRev }`; the protocol names the same two values `{ expectedRev, currentRev }`, and since both live in this repository and the package is unreleased, Surface changed rather than the protocol carrying two spellings. The bridge reads the envelope's `expectedRev` first and the old `input.expectedRev` second, so the dynamic affordances that bind `expectedRev` into the act input keep working for one release while agents move to the envelope.

## Generate

**Actions are generated from the definition that already governs the application's behavior, not written beside it.** The trials behind Surface measured the failure mode of hand-written actions: they are a second description of the same operations, and the two descriptions diverge the first time one changes without the other. `@axe/surface` answers that for live UI state. `@axe/generate` answers it for the common case of an application that already has a typed definition of its operations, an OpenAPI document, a table of zod-typed server functions, or a tRPC router. The manifest is derived from that definition on every build, so a renamed parameter or a new endpoint changes the manifest without anyone remembering to. The audit still checks parity afterward, but the thing it checks is no longer hand-copied.

**The generator refuses to invent what the definition does not say.** An OpenAPI operation without a description is left out with a warning naming the operation and the field, not given a description assembled from its path. The same holds for the risk of a mutation, for display hints and the human URL they point at, and for examples. These are exactly the fields the honesty rules exist for, and a generated guess would be a lie with better provenance. Overrides are the place for the author's words; the generated module `axe generate --code` writes has one TODO per gap so the review is a checklist rather than a search. Titles are the exception: a title derived from an operationId is a label, not a claim, and the author sees it in the review.

**Reads default to risk `low`, not `none`.** `none` means reading public data. The generator cannot tell public data from a customer's order history, so it declares the more cautious level and lets an override say `none` for public reads. Mutations default by method (`POST`, `PUT`, `PATCH` medium; `DELETE` high) because the document says nothing about consequences; `reversible` defaults to false for the same reason.

**The OpenAPI subset is deliberately limited.** The converter handles objects, arrays, primitives, enums, formats, nullability, local `$ref`s, a shallow allOf merge, and anyOf/oneOf as unions, and turns everything else into `z.unknown()` with a warning that names the path. A full JSON Schema implementation would be larger than the rest of the package, would still produce Zod schemas that `z.toJSONSchema` cannot round-trip, and would hide from the author which parts of their input an agent is no longer told about. A warning at the exact path is more useful than silent breadth.

**Cookie parameters and non-JSON bodies are skipped, not emulated.** The handler is a stateless HTTP call; it has no cookie jar and no multipart encoder. Both are reported per operation so the author can supply headers or exclude the action.

**Upstream authentication is opt-in, per option.** The generated handler sends no credentials unless `auth.forward` copies the incoming `Authorization` header or `auth.token` produces one from the AXE call. Forwarding an agent's bearer token to an upstream by default would make the AXE server a credential relay the site never chose.

**The tRPC adapter is structural.** It reads `_def.procedures`, `_def.inputs`, `_def.output`, `_def.meta`, and calls through `createCaller`, which is the shape of tRPC v10 and v11 routers, and it depends on nothing from tRPC. When a version changes that shape, the fallback is `fromFunctions`, which is what the adapter feeds anyway.

**`axe generate` reads JSON only.** No YAML parser is a direct dependency of the repository, and a YAML library is not tiny. The command names the one-line conversion instead.

## Client trust

**The client anchors credentials at the discovery origin, not at the manifest's `baseUrl`.** A manifest is a document the site serves, and anything that can serve it (a compromised page, a stale CDN object, a hostile tenant on a shared origin) could name another origin as `baseUrl`, `live.url`, or `pollUrl`. The origin the operator typed is the only one the operator chose, so it is the anchor, and every other origin needs an explicit `trust.origins` entry. A manifest handed to `new AXEClient` directly is trusted at its own `baseUrl` origin, because then the caller chose the manifest; a manifest that came from `discover()` remembers where it was found (a module-level `WeakMap`), so `discover()` then `new AXEClient(manifest)` anchors the same way as `AXEClient.discover`. `allowCrossOrigin` exists for agents that browse many sites, and it contacts other origins without credentials, which is the only safe meaning it can have.

**Credentials never cross an origin on a redirect, even to an authorized origin.** Following a redirect is the site's choice, not the operator's. Checking the target and then stripping credentials costs one anonymous request in the rare legitimate case (an apex-to-www move) and removes a whole class of leaks, including the one Node's `fetch` leaves open: it drops `Authorization` across origins but forwards every custom header. Redirects are followed with `redirect: "manual"` so each hop is checked before it is requested. Browsers hide manual redirect targets, so the browser build refuses redirects outright rather than follow one blind.

**Plain http to loopback is allowed by default.** The review asked for https except an explicit local-development allowance. The allowance is explicit in the sense that matters: http is accepted only for a loopback origin that is itself in the credential audience, which means the operator typed it or listed it. A remote manifest cannot introduce an http destination, because other origins need `trust.origins`, `allowCrossOrigin` never extends to http or to loopback names, and an https-to-http redirect is refused. Requiring a flag for `axe inspect http://localhost:3000` and every local test would push people to set `allowHttp: true`, which is worse. `allowHttp: false` exists for servers.

**URL checks are documented as half a boundary.** The client can refuse by origin and by the spelling of a host, and `destinationPolicy` lets an operator bind it to an allowlist. None of that sees the resolved address, so DNS rebinding and public names pointing at private addresses pass. The docs say so and point host-side deployments at an egress policy, rather than claiming the client prevents request forgery.

**`axe_poll` remembers the URLs it issued instead of changing the tool's input.** Polling by an opaque operation id would have changed the tool schema that models and hosts already see. Remembering the `pollUrl` of every `pending` result the server returned, bounded to the most recent 1000, keeps the tool unchanged and makes the model-supplied string a lookup key rather than a destination. A restarted server forgets them, which costs a restarted action, not a leak.

## MCP over HTTP (review 2026-09-24, items 9 and 10)

**One MCP server per session or per request, over one shared bridge.** The SDK's Web-standard transport serves one client: a stateless transport answers one request, a stateful one belongs to one session. `serveHttp` keeps what is expensive and shared (the AXE client, the manifest and its freshness, list-change subscriptions) in a bridge built by `createMcpServer`, and builds the cheap part, an MCP `Server` with its two handlers, per session or per stateless request. Stateless stays the default because it needs no affinity behind a load balancer; sessions are opt-in for hosts that want server-pushed `tools/list_changed`.

**Identity comes from each request, never from the session.** The MCP security guidance says a session is not an authentication, and tokens refresh within a session. The CallTool handler receives the request's verified `AuthInfo` from the SDK and calls `clientFor` for every tool call, so a refreshed token takes effect at once and a session id alone gets nothing. Sessions are also bound to the principal that opened them (`sub`, else a hash of the token), and a mismatch is a 404 like an unknown session, so a guessed session id reveals nothing.

**`clientFor` returns options, not a client; shared credentials are refused.** The bridge builds a client per call from the current manifest, so freshness and the trust policy apply to every caller. Callers never inherit `auth` or `headers` from `createMcpServer`'s options, and `serveHttp` refuses to start when those would silently act for every HTTP caller, unless `allowSharedCredentials` says the endpoint has one user. For an in-process site the caller's identity goes through the runtime's adapter context, the same path a framework adapter uses, rather than a synthetic bearer token the site's `authenticate` would have to accept.

**The MCP access token is not forwarded by default.** The review suggested forwarding the caller's bearer to a URL source. The MCP authorization specification forbids token passthrough: the token was issued for the MCP server. The docs show a per-caller token exchange in `clientFor`, and say that forwarding the same token is correct only when one authorization server issued it for both audiences. Nothing in the package makes passthrough the easy path.

**`@axe/mcp` is a resource server, not an authorization server.** It verifies tokens through the SDK's `OAuthTokenVerifier` interface, answers 401 and 403 with `WWW-Authenticate` (`resource_metadata`, `scope`), and builds the RFC 9728 document. The SDK's own bearer middleware and metadata router are Express-only; the Web-standard handler reimplements the same responses in a few lines instead of pulling Express into a package that runs on Workers.

**Freshness is a bound plus two triggers, not a poll loop.** A remote manifest is revalidated when it is older than the smaller of `manifestMaxAgeMs` and the site's max-age, when a tool call names a tool the copy lacks, and after `not_found`. Revalidation is a conditional request, so an ETag on the manifest (added to `@axe/core`) makes the eager setting cheap. There is no background timer in the package; `refresh()` exists for hosts that want one, as the docs show. Notifications compare the derived tool list, not the manifest, so a new `live.rev` does not send `tools/list_changed`.

**Retry identity is an optional `idempotencyKey` argument, not deduplication by input.** Two calls with identical arguments may be two intended orders, so the bridge never infers a retry from matching inputs: without a key every call gets a fresh one. With a key the site's operation claim ([P-OP-1]) already gives the right answers (stored envelope, `in_progress`, `conflict` for different input), so recovery is repeating the call, and no separate status tool was added. The argument reuses the envelope field's name so there is one word for one idea.

## Limits and schema boundaries (review 2026-09-24, item 12)

**An oversized body is `invalid_input` with a reason, not a new error code.** The error codes are a closed list that every agent switches on ([P-ERR-1]); a tenth code would reach agents built against nine as an unknown value. `invalid_input` is already what the agent must fix before retrying, `retryable: false` says not to repeat it, and `details.reason: "payload_too_large"` follows the precedent of `json_required` on `unsupported`. The HTTP status is 413 rather than the mapped 400, because proxies, load balancers, and logs already understand 413; agents decide by the body ([P-INV-7]), so the exception to [P-INV-6] costs them nothing.

**1 MiB by default, even though `document.base64` allows 10 MiB.** Every site pays for the body limit; few accept inline documents. A default sized for the largest kind would let any anonymous caller make every site buffer 14 MiB per request. Sites that take inline documents raise `maxBodyBytes`, and the kind registry says so; everything else uses `document.url`.

**Nesting is capped at 64 levels, fixed.** A 400 KB body of nested arrays overflowed the stack in the canonical JSON hash before any schema ran. No real request envelope needs more than a handful of levels; a configurable limit would be a knob nobody should turn.

**The in-memory stores sweep on writes and run no timer.** A background timer would need `unref`, a lifecycle, and a way to stop it in tests, and it would still only matter for a process that writes nothing (whose map is not growing). Sweeping at most once per `sweepIntervalMs` on a write bounds the cost and the memory with none of that; `close()` exists to release memory, not to stop anything. `maxEntries` evicts oldest first but never a claim whose lease is running, because evicting one would let the operation run twice; a store full of running claims throws, which surfaces as a failed request rather than a duplicate charge.

**The fingerprint is `input` as sent.** Phase 1 hashed the parsed input. With a transform to a `Date`, every input hashed the same (`{}`), so a reused key with a different date replayed the first result; a `BigInt` would have thrown. The raw input is always JSON (it came from `JSON.parse`), and the retry of an action that no longer exists could only ever be matched on it. The cost is that two bodies the schema would parse identically (one spelling out a default) are different operations under one key, which an agent resending its own body never hits.

**The validator fails closed; it is not Ajv.** Measured with esbuild for the browser: the in-house validator is 10 kB minified (3.6 kB gzipped); Ajv 8's draft 2020-12 entry is 134 kB (40 kB), 148 kB (44 kB) with `ajv-formats`. It ships in `@axe/surface`'s browser entry (held under 50 kB, no Zod), and Ajv compiles schemas with `new Function`, which strict CSPs and Cloudflare Workers refuse. Instead of growing toward full JSON Schema, the subset covers what Zod emits and the kinds use, implements the cheap remaining 2020-12 keywords, and refuses the value for anything else: a keyword it does not know, a format it cannot check without a pattern, a pattern that does not compile, an unresolvable or non-local `$ref`, a `$ref` loop that consumes nothing. Ignoring any of those would accept what the author meant to refuse. `schemaProblems` and the lint report the same constructs at build time, so a refusal in production is a lint warning somebody ignored.

**Unknown formats pass when a pattern carries them.** Zod emits a `pattern` next to almost every `format` it writes (`cuid2`, `e164`, `emoji`, `starts_with` in an `allOf`), and the pattern is the check. Refusing those formats would break continuation payloads built from ordinary Zod schemas; accepting any format with no pattern would silently widen. So a format is accepted only when the validator checks it or a pattern in the same schema does.

**Refinements are marked in the manifest and linted, not rejected.** A `.refine` cannot be written in JSON Schema, and rejecting refined schemas at registration would forbid ordinary validation (a weekday, a date after another). Publishing the looser schema without saying so would tell agents a value is valid when the server will refuse it. `x-axe-refined: true` on the node is standard JSON Schema (an annotation), costs nothing to agents that ignore it, and lets an agent expect `invalid_input`; the `refined-schema` lint warning makes the author decide whether the description explains the rule. Transforms and defaults are not marked, since they change what the handler receives, not what the agent may send; coercion makes the server more permissive than its schema, which is safe.

**The backtracking check is a heuristic lint warning.** Deciding whether a regular expression backtracks catastrophically needs an automaton analysis this package should not carry. The shape behind nearly every real incident, a repeated group whose body ends in an unbounded repetition, is cheap to recognize, and none of Zod's built-in patterns match it. It warns rather than refuses because false positives are possible and the pattern is the site's own.

**The client checks documents by hand, not with the core Zod schemas.** Validating with `@axe/core/schemas` would pull Zod into `@axe/client`, which is dependency-free and was 12 kB. The hand checks cover the members the client and `present` read, per status, and fail with an `AXEClientError` naming the member. With timeouts, bounded reads, and polling budgets the entry is 16 kB, so the bundle budget moved from 15 kB to 18 kB.

**Client timeouts use a plain timer, not `AbortSignal.timeout`.** One `AbortController` per call is aborted by the caller's signal or by an `unref`'d `setTimeout`, and the timer is cleared when the body finishes. `AbortSignal.any` is missing from Node 20.0–20.2, and `AbortSignal.timeout` cannot be cleared early, so a finished request would keep its timer (and, in a short-lived process, keep the process alive until it fired).

## Existing agent interfaces (review 2026-09-24, item 14)

**WebMCP is a subpath of `@axe/surface`, not a package.** The adapter needs `describeEntry` and the `Surface` type and nothing else; a separate package would depend on `@axe/surface` anyway and add a release unit. A subpath keeps the dependency direction one way (the adapter imports the core, never the reverse), and the bundle test pins that `@axe/surface` and `/react` do not pull it in. It costs about 5.6 kB minified on a page that already has the surface.

**Written against the current draft only, behind one indirection.** The WebMCP draft moved from `navigator.modelContext` with `provideContext`/`unregisterTool` to `document.modelContext` with `registerTool(tool, { signal })`. The adapter implements only the shape the draft and Chrome's documentation state on 2026-09-24, finds it in one function, and registers through another; supporting the older shape would mean implementing an API nobody documents any more.

**No tool for a sensitive field, and none for the ledger.** A browser agent could type into a PIN field through a tool as easily as through the page, but the point of `sensitive` is that a person enters it. The ledger can hold typed text under the `keep` policy; `expose` still publishes it inside the page for agents that already drive it.

**Omitted `expectedRev` means the current revision.** WebMCP agents call tools from the page's own tool list, re-registered as availability changes, so requiring a revision would force an observe round-trip before every click. The surface's availability and confirmation checks still apply, and an agent that planned on an observation can pass its `rev` to be refused if the page moved.

**Tool names use only letters, digits, `_`, and `-`.** The draft also allows `.`, but agents hand these tools to model APIs, several of which refuse dots. A colliding id gets a hash of the id, not a counter, so a name never depends on registration order.

**Elicitation walks `accepts` in the site's order and stops at the first sensitive kind.** Skipping a preferred sensitive option to put a less preferred one in a form would steer the user away from what the site asked for first. A kind that is not sensitive but has no flat form is skipped, because the model can still supply it. Payment and identity kinds are sensitive for this purpose whatever their flag: MCP forbids payment credentials in forms, and `payment.wire-confirmation`, though not sensitive in the kind registry, is a payment step that belongs on the site's page.

**URL-mode `accept` is not completion, and `login_required` is not offered.** The bridge cannot know when the user finishes on the site, so it returns the resume token to the model as before rather than waiting. Signing in to the site the bridge speaks for is what MCP authorization is for; the elicitation specification says URL mode must not be used to authorize the user to the server itself.

**The Apps view renders the SDK's escaped HTML, delivered in the result's `_meta`.** The view is one static resource that a host may prefetch and cache, so per-call data has to arrive with the result. Rendering `toHTML` output keeps one renderer; the view parses it with `DOMParser` (no script runs), removes scripts, handlers, and the affordance buttons, and never evaluates result data. The server declares the `resources` capability for every client because capabilities are announced before the client's are known; the resource is listed and linked only for hosts that negotiated the extension.

## Human oversight and execution modes (review 2026-09-24, items 13 and 15)

**An approval is a handoff with bindings, not a new token.** Phase 1 already gave the resume token everything an approval must be bound to except the state: the action, the input fingerprint, the principal, the tenant, an expiry, single use through the operation claim, and replay of the stored envelope. A separate approval token would have duplicated that machinery and its tenant and principal checks, and every refusal rule written for it. So `requestApproval` is a handoff whose token record also keeps the input as sent, the state `approvalState` reported, and the decision. The agent's side is unchanged: `needs_human`, a link, `/axe/resume`.

**The runtime computes the bound state; the handler does not pass it.** A handler that passed its own state value could pass the wrong one, or one read before a write it then forgot. `approvalState` is one function the runtime calls at the request, at the approval, and at the resume, so the three comparisons cannot use different definitions. The cost is a small window between the handler reading the state for its preview and the runtime reading it for the binding; the approval page renders the current state from the site's store, and a moved state is refused at approval anyway.

**Invalidation is permanent.** A state that changed and changed back (an edit undone) would make a stale approval valid again under an equality check alone, after the person has seen a different plan. Once a mismatch is observed, the request is invalidated for good and the agent asks again. With a revision counter the question never arises; with a status or a content value it would.

**Approval is recorded by the site's code, never inferred from a request.** The SDK cannot see a browser, a session, or a click. `approveHandoff` takes the approver's name from the site, after the site's own session check, CSRF protection, and authorization. Nothing reaching the AXE endpoints (an input flag, a payload, a resume body) can set it; a test sends `confirm: true`, `approved: true`, and `approvedBy` on the resume and gets `handoffStatus: "open"`. Whether a person may approve their own agent's request is the site's policy; the reference app lets an approver do so and refuses a planner.

**Cancel applies to every handoff, and not to committed work.** A person who declines a signature request should be able to say so, not wait for expiry, so `cancelHandoff` works on any unused handoff. A handoff whose resume ran, or is running, answers `used`: the effect happened, and pretending to cancel it would be worse than refusing. Undo is an action of the site's own; `reversible: true` describes one and implements nothing.

**Decisions are read-modify-write on the `TokenStore`, like `completeHandoff`.** Making them atomic would need a compare-and-set on `TokenStore`, a breaking interface change for every store adapter, for a race between two people deciding the same request within milliseconds. The resume re-reads the record after it claims the operation, which closes the common interleaving (a cancel before the resume starts); the handler's conditional write at the bound state is the guarantee against running on changed state. The limit is documented.

**Approval events come from the runtime, not the handler.** The lifecycle has transitions no handler sees (approval and cancellation happen on the site's page, invalidation inside the runtime). Emitting them as action events on the existing `onActionEvent` channel gives a site one feed for its history, under the existing rule that action events carry identifiers and actors and never payloads.

**Execution modes are a spec section, because the absence of a broker is a property integrators rely on.** A reviewer's reading of the React hook plus a Next route suggested one registry; there are two, and nothing connects them. Stating it as [S-MODE-1] to [S-MODE-4] gives WebMCP and other in-page adapters a rule to build against (connect explicitly, state the scope) and tells integrators where shared state must live (the server, behind a conditional write).

**The reference app is a workspace package outside the build graph.** It depends on Next and React 19, which the SDK packages must not; it has no `build` script, so `pnpm -r build` does not run `next build`, and its Node suite runs in `pnpm -r test` because it is fast and deterministic. The browser suite needs a production build and Chromium, so it has its own script, the way the site's does. Server state is in memory behind a conditional write that has no `await` between the check and the write: the same semantics as `UPDATE ... WHERE rev = $expected`, without adding a database dependency to the repository.
