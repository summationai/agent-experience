# Changelog

All packages version together. Entries are generated from changesets on release; this file also records protocol-level changes by hand.

## 0.1.0 (unreleased)

Initial release of the Body Spray SDK and the `axe/0.1` protocol.

- `spec/`: AXE-PROTOCOL.md, KINDS.md, EVENTS.md, VOCABULARY.md, generated JSON Schemas.
- `@axe/core`: `createAXE`, `action`, result envelope, escalation ladder with signed tokens, idempotency, auth modes with login handoff, multi-tenant manifests and platform index, display and affordance validation, well-known kinds, honesty lints, events and sinks.
- `@axe/client`: discovery, invoke/continue/resume/poll, `run()` with fulfillers, `present`/`toMarkdown`/`toHTML`.
- `@axe/mcp`: derived MCP server over stdio and Streamable HTTP.
- `@axe/express`, `@axe/next`, `@axe/fetch`: adapters.
- `@axe/testing`: conformance suite, AXE audit, vocabulary drift check, test helpers.
- `axe` CLI: init, validate, inspect, preview, conformance, audit, mcp.

### Request policy (review item 6)

- Protocol §6.4, [P-TRANS-1] to [P-TRANS-4]: a `POST` to a state-changing endpoint (an action that is not `readOnly`, `/axe/continue`, `/axe/resume`) must be `application/json` or `application/*+json`, else `unsupported`; a `POST` carrying ambient credentials from an origin that is neither the site's (from `baseUrl`, never `Host` or forwarded headers) nor trusted is `forbidden`, the same response for every path; requests with neither `Origin` nor `Sec-Fetch-Site` pass the origin rule.
- `@axe/core`: `createAXE({ requestPolicy: { requireJsonContentType, trustedOrigins, originCheck } })`, applied at the entry of `handle()` before any body, identity, or token is read. Defaults: JSON required on writes; origin checked on any `POST` with a `Cookie` header; origins with credentialed `cors` trusted. Refusals carry `details.reason` `json_required` or `cross_origin_refused`. Pure functions exported (`evaluateRequestPolicy`, `resolveRequestPolicy`, `isJsonContentType`, `isAcceptedOrigin`). Migration: a caller that posts JSON to a mutating action without `Content-Type: application/json` now gets `unsupported`; `@axe/client`, `@axe/mcp`, and the conformance suite already send the header.
- `@axe/express` and `@axe/next` (Pages): the adapters keep the `Content-Type` the client sent instead of relabeling a parsed body as JSON, and the Express adapter reads the raw stream while it is unread (Express 4 leaves `req.body = {}` on a body its json parser skipped).
- `@axe/testing`: conformance check `runtime.json-content-type`.

### Surface

- `spec/SURFACE.md`: the Surface contract (v0.2), ported from the sumapps trials and rewritten on top of the AXE envelope: live controls with `state.reason`, `effect` as AXE risk metadata, one revision per application, refusals as `conflict` / `not_found` / `invalid_input` / `unavailable`, and `requires` (AXE kinds) plus `handoff` on unavailable controls.
- `@axe/surface`: `createSurface` (registry, `observe`, `act`, revision, ledger, `expose`), `@axe/surface/react` (`useSurface`), and `@axe/surface/axe` (`surfaceActions`: any surface becomes an AXE manifest with `<ns>.observe`, `<ns>.ledger`, and one action per entry, refusals mapped onto the ladder, `continue` running the application's `fulfill`).
- Vocabulary: a "Surface" section in `spec/VOCABULARY.md` (entry kinds, ops, field names, API names) so the drift test covers the new package.
- Two defects from the first staging trial pinned as contract rules with tests: `act` refuses any `target` that is not a non-empty id or a non-negative integer index as `invalid_input` before any lookup, an index never resolves to a row without one, and the revision guard runs before resolution ([S-ACT-6..8]); applications must re-register on transient states ([S-REV-5]), with `freeze(reason)` / `thaw` as the first-class helper: every entry unavailable with the reason, `observe().frozen`, acts `unavailable`, revision moved on both ends, nested freezes counted ([S-FRZ-1..4]).
- DOM mirror: `surfaceAttributes`, `surfaceSelector`, and `describeEntry` in `@axe/surface`, and `useSurfaceProps` in `@axe/surface/react`, so the accessible name a browser agent or screen reader reads is the entry name by construction. Spec §7 is now a rule set: [S-DOM-1] (name wording and the attribute set), [S-DOM-3] (the selector contract), [S-DOM-4] (the one-line description); a `domAttribute` vocabulary category names the attributes.
- Ledger (`spec/SURFACE.md` [S-LED-1..7]): every `act`, run or refused, appends `{ seq, at, op, target, actor, revBefore, revAfter, status, text?, changed }`; `ledger({ since, actor, limit })` reads it oldest first under bounded retention (`ledger.max`, default 1000); `observe()` carries `ledgerSeq` and every act result its `seq`; `expose` publishes `ledger`. The bridge adds `<ns>.ledger` (read-only, with `display`) and emits one action event (`surface.act`) per act on the server's `onActionEvent` sinks ([S-AXE-4]). In `@axe/core`: action events (`spec/EVENTS.md` [E-5..7], `schemas/action-event.schema.json`), `emit` on the handler context, `onActionEvent` on `createAXE`, and `consoleSink`/`jsonlFileSink` accept them.

### Live state

- Protocol §21 (additive, still `axe/0.1`): a site MAY publish a revision. Every result envelope gains optional top-level `rev`; requests to `/axe/actions/{name}`, `/axe/continue`, and `/axe/resume` gain optional `expectedRev`; a stale `expectedRev` is `conflict` with `details: { expectedRev, currentRev }` and nothing applied, checked after the idempotency replay and before the handler or a login handoff. Actions gain optional `availability` (`{ available, reason?, requires?, handoff? }`), the manifest gains `live: { rev?, url? }`, and `GET /axe/state` serves `{ rev?, actions }` per caller with `Cache-Control: no-store`. `unavailable` errors MAY carry `details: { reason, requires?, handoff? }`. Rules P-LIVE-1 to P-LIVE-10; `spec/schemas/state.schema.json`.
- `@axe/core`: `createAXE({ revision })`, `action({ availability })`, handler context `availability` and `expectedRev`, `unavailable()` helper, `describeLive()`, lint rule `unavailable-without-reason`.
- `@axe/client`: `expectedRev` on `invoke`, `continue`, `resume`, and `run` (tracked through the ladder), `state()`, `live()`, `stateToMarkdown`; `present` carries `rev` into `toMarkdown` and `toHTML`.
- `@axe/mcp`: `axe_state` tool when the manifest carries `live`, `expectedRev` argument on action tools, availability in tool descriptions, stale `conflict` and `unavailable` explained.
- `@axe/testing`: six `live.*` conformance checks (skipped without `live`), audit check `actionable.live-state`.
- `@axe/surface`: a stale act's `details` are `{ expectedRev, currentRev }` (was `{ rev, expectedRev }`); `surfaceActions` reads the envelope's `expectedRev`; pass `revision: surface.currentRev` to `createAXE`.

### Surface: one action per control (contract v0.3)

- `spec/SURFACE.md` §6 rewritten: every entry is its own AXE action ([S-AXE-1], [S-AXE-6]), named `<ns>.<slug>` by a deterministic, collision-safe, reversible rule ([S-AXE-7]), with the entry's live state as its `availability` ([S-AXE-8]) and the set following the registry ([S-AXE-9]). [S-OBS-3] adds `entries()`, `registryVersion()`, and `availability(id)` to the surface.
- Removed before any release: the generic `<ns>.act` action of contract v0.2, its `target`/`op` input, and the deprecated `input.expectedRev`. The revision travels only as the request envelope's `expectedRev`; `observe`'s per-row affordances name the row's own action and carry `expectedRev` for the envelope.
- `@axe/surface/axe`: `surfaceActions` returns an `ActionProvider` (`axe.addProvider(surfaceActions(surface))`) with `actionNameFor`, `entryIdFor`, and `onChange`; `entrySlug` exported; options `fields` (risk and reversibility declared for field entries) and `onError` (an entry whose text fails the honesty lint is reported and left out). `observe` and `ledger` carry examples, so the conformance suite's `live.*` checks run against a surface.
- `@axe/core`: `ActionProvider`, `axe.addProvider(provider)`, and `axe.onActionsChanged(listener)`; providers are consulted after registered actions wherever actions are enumerated or looked up, with name uniqueness and auth modes still checked. A retried `idempotencyKey` for an action that has since left the set is answered from the idempotency store before `not_found` ([P-IDEM-2]). Dynamic affordances may carry `expectedRev` ([P-AFF-4]; `DynamicAffordance`, `ResolvedAffordance`, `schemas/manifest.schema.json`).
- `@axe/mcp`: for an in-process `AXE` source the tool list is derived on every `tools/list`, tool calls resolve against the current manifest (with an idempotency key supplied for mutating actions the client's snapshot did not know), and the server declares the list-changed capability and sends `notifications/tools/list_changed` when `onActionsChanged` fires.

### Surface: integration fixes (contract v0.4)

What the first integration into a legacy-DOM application asked for, made general.

- Browser bundling: `jsonlFileSink` moves to `@axe/core/node`, the one entry of `@axe/core` that needs Node; it is no longer exported from `@axe/core` or `@axe/core/events`. A browser bundle importing `@axe/surface` no longer meets `fs/promises`. New zod-free subpath `@axe/core/json-schema` (`validateJsonSchema`, `schemasStructurallyEqual`, `deepEqual`). A bundle test in `packages/surface/test` builds `@axe/surface` plus `@axe/surface/react` for the browser with esbuild and fails on a Node built-in, on Zod, or above 50 kB minified (about 21 kB today, from a build that failed and, with the built-in aliased away, 515 kB).
- Zod-free surface ([S-ENT-3]): `@axe/surface` and `@axe/surface/react` import nothing that carries Zod. `edit.schema` is a JSON Schema or a Zod schema; a Zod schema is detected structurally (`safeParse`), validated by calling it, and published in `observe()` through `createSurface({ toJsonSchema })` (pass `toJsonSchema` from `@axe/core`), which the `requires` schemas from `accept()` need too. Registering a Zod schema without the converter throws with that instruction. `@axe/surface/axe` still carries Zod through `@axe/core`.
- Revision modes ([S-REV-1], [S-FRZ-2], [S-FRZ-3]): `surface` (the application calls `bump`) or `app` (it adopts a server revision with `setRev`), inferred from the last call or pinned with `createSurface({ revision })`; `revisionMode()` reports it. In `app` mode `freeze` and `thaw` leave the revision alone and still report the freeze and notify `onChange`, so an act planned before a freeze is `unavailable` while frozen and accepted after the thaw exactly when the application's revision did not move.
- Handler reports ([S-ACT-1], [S-LED-5]): a handler, `edit.set`, or `more` may return `{ changed?, rev? }`; `act` folds `changed` into the output and the ledger and adopts `rev` as `setRev` would before building the result. `HandlerReport` type.
- Live DOM mirror ([S-DOM-1]): `surface.attributesFor(id)` returns `{ set, remove }` from the live availability, so a freeze shows with its reason and a stale reason is removed; `SURFACE_ATTRIBUTES` lists every attribute the mirror may set. `surfaceAttributes(entry)` stays for a one-time render. `useSurfaceProps` follows the live availability and re-renders when it changes.
- Bridge ([S-AXE-2], [S-AXE-6], [S-LED-1]): a collection without `more` has no action (it stays a row of `observe`); entry input schemas describe the shape only (`text` a string, `confirm` an optional boolean), leaving `maxLength`, the field's schema, and a required `confirm` to the surface so every such refusal is ledgered and emitted; `needs_human` only for a handoff with a `url`.
- Handoff without a `url` ([S-AV-3]; protocol [P-LIVE-5], [P-LIVE-9]): `HandoffSpec.url` is optional on an unavailable action's `handoff`, for a step taken inside the application with no page of its own. It is reported in `availability` and in `error.details.handoff` and never becomes `needs_human`, whose Handoff stays complete ([P-HAND-1]). `spec/schemas/state.schema.json` and `manifest.schema.json` follow.
- `createAXE` defaults `auth` to `{ modes: ["none"] }`; an explicit empty `modes` is refused with a message that says to omit `auth` for a public site.
- Consuming from a checkout: `scripts/pack-for-consumer.sh <out-dir>` builds and packs core, surface, client, and testing and writes a `SOURCE` file; `docs/deploying.md` ("Consume from a checkout") covers `file:` dependencies, the overrides for packed siblings, and copying tarballs into place before installing from a lockfile.
- Vocabulary: `attributesFor`, `revisionMode`, `SURFACE_ATTRIBUTES`; `jsonlFileSink` now under `@axe/core/node`.

### Surface: write preconditions (contract v0.5)

- Ordering ([S-ACT-9]): acts on one surface run one at a time, in call order. Every pre-handler check runs when `act` is called, so a refusal never waits; an act that waits behind another is checked again when it reaches execution (revision, target, freeze, availability), and is `conflict` or `unavailable` with no handler run when a predecessor's commit, a person's `bump` or `setRev`, or a freeze intervened. Before, two asynchronous acts presenting the same `expectedRev` both ran and both returned `ok`. `observe`, `availability`, and `ledger` do not wait.
- A commit that leaves an app-owned revision in place ([S-ACT-10]) closes the claims taken before it at that revision, unless it provably changed nothing (`changed: []`); an act claimed after it is accepted.
- The handler's own precondition ([S-ACT-11]): handlers, field setters, and `more` receive an `ActContext` (`{ id, op, expectedRev, actor }`) as their last argument for a conditional write, and refuse by throwing `SurfaceConflict` (new export) or returning `{ conflict: { currentRev? } }` in the `HandlerReport`; `act` returns `conflict` with `details.currentRev`, ledgers a refusal, and adopts nothing.
- A stale handler report ([S-REV-6]): a reported `rev` lower than the surface's revision when the handler settles is not adopted; the ledger entry carries it as `ignoredRev` (also in `<ns>.ledger` output).
- Bridge ([S-AXE-4]): the entry action passes the envelope's `expectedRev` to the queued act, so the server's check is the first gate and the surface's the second; a test drives two concurrent invocations through `axe.handle`.
- Vocabulary: `SurfaceConflict`, `ActContext`, `ignoredRev`, the handler report's `conflict`.
### Surface: authorization and privacy (contract v0.5)

- `spec/SURFACE.md` §6.1 ([S-AUTH-1] to [S-AUTH-6], [S-PRV-1] to [S-PRV-3]); [S-LED-1] and [S-DOM-2] updated. From the 2026-09-24 review, item 5.
- `@axe/surface/axe`: every generated action declares `auth`, default `user`; a server whose `auth.modes` lacks `user` (including `createAXE`'s public default) refuses the bridge on its first request. Options `auth`, `read` (observe and ledger), `authFor(entry)`, `template`, `redactEvent`. `surfaceActions` accepts a resolver `(context) => Surface | null` in place of a surface, with a `template` for the action set; `scopedSurfaces({ create, key, max, idleMs, now, onEvict })` builds one keyed by tenant and principal. Availability for an unidentified caller never reads a protected surface. Types `SurfaceContext`, `SurfaceResolver`, `ScopedSurfaces`, `ScopedSurfacesOptions`.
- `@axe/surface`: field entries take `sensitive: true` (no `value` in `observe()`, `describeEntry` says `value hidden`, no ledger text); `createSurface({ ledger: { text: "keep" | "hash" | "omit", redact } })`; ledger entries may carry `textHash`. Types `LedgerOptions`, `LedgerTextPolicy`.
- Migration: a bridge that should stay public passes `auth: "none"`; otherwise add `user` (or `site`) to the server's `auth.modes`. Docs examples now pass `auth` explicitly.
- Vocabulary: `scopedSurfaces`, `authFor`, `redactEvent`, `idleMs`, `onEvict`, `keyFor`, `textHash`; `sensitive` also names the Surface field flag.

### Surface: mounted React behavior (contract v0.6)

- `@axe/surface/react`, `useSurface` and `useSurfaceProps` (review item 11): the registration belongs to the entry's `id` and the target surface. A change of either unregisters the previous pair and registers the new one; before, an id change left the old id registered (and unmount then removed the old id, leaving the new one), and a target change registered nothing in the new surface. An act now runs the latest render's `handler`, `edit.set`, `more`, and `requires.fulfill` through a stable wrapper, whatever `deps` list; before, it ran the closure from the render that last changed `deps`. Registration runs in a layout effect (a passive effect on the server). `useSurfaceProps` subscribes once rather than on every render.
- `@axe/surface`: `surface.subscribe(listener)` ([S-OBS-4], additive): called after every `register`, an `unregister` or `reconcile` that removed a row, `bump`, `setRev`, a `seedRev` that adopted a revision, `freeze`, `thaw`, and `reset`. `useSurfaceProps` reads through it, so a registration made outside the component reaches the control. `onChange` is unchanged and still does not fire on registration, so the bridge's change notification (and MCP `tools/list_changed`) is not sent once per row.
- `spec/SURFACE.md` v0.6: [S-OBS-4]; [S-ENT-5] and [S-DOM-1] state the React hooks' ownership, latest-handler, and Strict Mode rules.
- Tests: `packages/surface/test/react-mounted.test.ts` mounts the hooks with `react-dom/client` under jsdom (`jsdom` is a devDependency of `@axe/surface` only; the bundle test checks it never enters the browser bundle). The browser bundle of `@axe/surface` and `/react` went from 25,290 to 26,308 bytes minified.
- Migration: none required. Code that listed handler inputs in `deps` only to keep the closure fresh can drop them. Code that relied on an id change keeping the old row (no known consumer) must register the old id itself. A non-React mirror that re-applies `attributesFor` on `onChange` should use `subscribe` under an application-owned revision.
- Vocabulary: `subscribe`.

### Generate

- `@axe/generate`: derive AXE actions from definitions an application already has, so the manifest follows the definition instead of being written beside it. `fromOpenAPI` maps every OpenAPI 3.x operation to an action (name from the operationId or the method and path, flags and default risk by method, auth from the security requirements, input from parameters plus the JSON request body, output from the 2xx response, an HTTP handler that maps upstream statuses to AXE error codes) with an in-house JSON Schema → Zod converter for the common subset. `fromFunctions` takes a table of zod-typed functions; `fromTRPCRouter` reads a tRPC router structurally, without depending on tRPC. `generate` merges sources, applies per-action overrides and a policy (`exclude`, `include`, `defaultRisk`, `maxRisk`, `requireInputDescriptions`), runs the honesty lints, and returns actions, warnings, and provenance; `registerGenerated` registers the result.
- Honesty: the generator never invents a description, a risk for a mutation, a display shape, or a human URL. An operation missing one is left out with a warning naming the operation and the field, until an override supplies it.
- `axe generate <openapi.json> [--base-url] [--out axe.json] [--code axe.ts]`: prints what was generated and why anything was left out, writes a static manifest for review, and emits a starter module with one TODO per gap. JSON input only.
- Docs: `docs/generating.md`. Vocabulary: `axe generate` and the `@axe/generate` API names.

### Client trust boundary (review 2026-09-24, item 3)

- Protocol §17.1, [P-AGENT-4] to [P-AGENT-9]: agent-side rules for where requests and credentials may go. Additive; no wire change.
- `@axe/client`: credentials (`auth` and `headers`) go only to the discovery origin (or, for a manifest passed to `new AXEClient`, its `baseUrl` origin) plus `trust.origins`. A `baseUrl`, `live.url`, `pollUrl`, `AXE-Manifest` header, or `axe-manifest` link on another origin is refused, or contacted without credentials when `trust.allowCrossOrigin` is set (loopback and private-range names stay refused). Redirects are followed by hand and re-checked per hop; credentials never cross an origin on a redirect; https-to-http is refused. Plain http only for authorized loopback origins by default (`trust.allowHttp`). `trust.destinationPolicy` gates every outbound URL. Refusals throw `AXETrustError` before anything is sent; `checkDestination(url)` answers without sending. `AXEClient.discover` throws when the manifest's `baseUrl` is not authorized. Behavior change: a client that relied on a cross-origin `baseUrl`, `live.url`, or `pollUrl` must list the origin in `trust.origins`; in browsers, a redirect is refused because its target cannot be checked.
- `@axe/mcp`: `axe_poll` polls only a `pollUrl` the server returned in a `pending` result; any other URL is refused without a request. Tool schema unchanged.
### Review 2026-09-24: token binding, site principals, operations

- Tokens ([P-TOK-6], [P-TOK-7]): every continue, resume, and poll is checked against the serving tenant and the acting principal before any hook runs or any stored result is returned; every refusal is the unknown-token `not_found`. A continuation minted on one tenant no longer runs on another. A token minted anonymously is refused with a user's credentials. `completeHandoff` takes `tenant` and refuses another tenant's handoff, a used one, a different user on a user-bound handoff, and a second user on a login handoff.
- Site keys: one principal for invoke, continue, resume, and poll, so a workflow started with a site key continues with it (it was `not_found`). A verdict without an `id` is scoped by an HMAC of the key. Keys are verified again on every follow-up. `siteKey` (`SiteKeyContext`: `id`, `actions`, `derived`) reaches `onContinue`, `onResume`, `onPoll`, availability hooks, and the `revision` provider (`RevisionContext.identity`, `RevisionContext.siteKey`).
- Poll ([P-POLL-1], [P-POLL-2]): authorized before a terminal result is returned (it was readable anonymously); one `onPoll` at a time per token.
- Operations (§12.2, [P-OP-1] to [P-OP-4]): `IdempotencyStore` is now `get`, `claim`, `complete`, `release` (breaking; no shim; `createAXE` refuses a get/set store). Concurrent calls with one key, and concurrent uses of one token, run once; the others get a retryable `conflict` with `details.operationStatus: "in_progress"` and `Retry-After`. A repeated successful continue or resume returns its original envelope instead of `conflict` ([P-REQ-9], [P-HAND-6]). `operationLeaseSeconds` config; `operationId` on handler contexts. `SqliteIdempotencyStore` in `@axe/core/node`. `TokenRecord.onBehalfOf` is now `principal`; `consumedAt` and `terminal` are removed.
- Conformance: `ladder.continue-replay` and `ladder.resume-replay` expect the original envelope; new `ladder.token-principal`.
