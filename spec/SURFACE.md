AXE as specified in `AXE-PROTOCOL.md` is outside-in: a site declares actions for the world's agents, with discovery, requirements, handoff, and resume. Surface is inside-out: a running application publishes its **live** state, with reasons and one revision, and an agent acts through the application's own controls. The two meet at a seam defined in §6: every control on the surface is served as its own AXE action, with the control's availability as the action's, and its refusals map onto the escalation ladder.

Surface came out of two trials on business applications with opposite shapes (state in the browser; state on the server with a protected mutation protocol). Its rules are the ones those trials needed and no more.

## 1. Terms

- **Surface**: an application's registry of its own controls, plus a revision.
- **Entry**: one registered control. Kinds: `action` (a button, a switch), `field` (an input, a cell), `collection` (a list or grid that can load more).
- **Revision** (`rev`): one integer for the whole application, moved by every change an agent could observe, whoever made it.
- **Observation**: an indexed snapshot of the entries at a revision, with domain objects.
- **Act**: running one entry's own handler, guarded by the revision the agent observed.
- **Actor**: who acted: `agent`, `user`, or an identity the application supplies.
- **Ledger**: the surface's record of every act and every refusal, in order, with the actor and the revisions each spanned.

## 2. The three rules

**[S-RULE-1] Surface reports; it never decides.** An entry's availability and reason are whatever the application computed to enable or disable its own control. The surface performs no authorization, validation, or business logic of its own beyond the checks in §5.

**[S-RULE-2] Same door.** An act runs the control's own handler, the one a click or keystroke runs, so authorization, validation, and persistence stay where they are. The surface introduces no second path to state.

**[S-RULE-3] One revision.** Every observation and every entry carries the application's revision; every act presents the revision the agent observed; an act whose revision has moved applies nothing.

## 3. Entries

**[S-ENT-1]** Every entry has a stable `id`, a `kind`, a `role`, a `name` that states the outcome in the application's own words ("Draft Jahmyr Gibbs (RB)", "Lock March"), and optionally the `object` it belongs to.

**[S-ENT-2]** An `action` entry has `state` (§4), `effect` (§3.1), and a handler `(actor, text, context)`, where `context` is the act's `ActContext` ([S-ACT-11]).

**[S-ENT-3]** A `field` entry has a `value` and an `edit` descriptor: read-only with a `reason`, or editable with an optional `maxLength`, an optional `schema` for the text, and a setter `(text, actor, context)`. The `schema` is a JSON Schema, or a Zod schema (anything with `safeParse`): the surface validates a Zod schema by calling it and publishes it in `observe()` through the `toJsonSchema` converter the application configures (`createSurface({ toJsonSchema })`, passing `toJsonSchema` from `@summationai/axe-core`); registering a Zod schema without a converter is an error. The surface itself never imports Zod, so a browser bundle of `@summationai/axe-surface` carries none.

**[S-ENT-4]** A `collection` entry has `total`, `loaded`, `filter`, and `sort`, and is actionable only when it can load more (`more(context)`).

**[S-ENT-5]** Entries are kept in registration order. Replacing an entry by id keeps its position, so an index observed for one row does not move because a sibling refreshed. Unregistering removes the row; `reconcile(prefix, keep)` removes every row under a prefix that a re-scan did not keep. The React hooks (`useSurface`, `useSurfaceProps` in `@summationai/axe-surface/react`) follow the same rule: a refresh when `deps` change replaces the entry in place, and a re-render with unchanged `deps` registers nothing. The registration belongs to the pair of the entry's `id` and the target surface: when either changes, the hook unregisters the previous pair and registers the new one (at the end of the table, as any new id), and unmount unregisters the current pair. The handler, `edit.set`, `more`, and `requires.fulfill` the surface calls are those of the latest committed render, whether or not `deps` list what they read. Strict Mode's extra unmount and mount leave the table as a single mount does, in render order. Two mounted components that register the same id on one surface share one row, and the first to unmount removes it; applications give each control its own id.

### 3.1 Effect

**[S-EFF-1]** `effect` carries AXE's risk metadata: `mutates` (the name of the state the action changes), `idempotent`, `reversible`, and `risk` (`none` is never valid for an action; the default is `medium`). `undoable` is a deprecated alias of `reversible`. `confirm: true` means the act must carry `confirm: true`. `text` is the prompt for free text the handler accepts.

**[S-EFF-2]** Effect metadata MUST be truthful (protocol [P-HON-7]). An action that changes state MUST NOT be presented as read-only; the surface has no read-only action kind for that reason.

## 4. Availability

**[S-AV-1]** An action's `state` is `{ available: true }` or `{ available: false, reason }`. `reason` is plain language in the application's words, present whenever `available` is false.

**[S-AV-2]** An unavailable action MAY declare `requires`: an ordered list of `accepts`-shaped entries (protocol §8, kinds from `KINDS.md`) that would make it available, with a `fulfill(kind, payload, actor)` the application runs when an agent supplies one.

**[S-AV-3]** An unavailable action MAY declare a `handoff` (`reason`, `instructions`, `whatAgentShouldSayToUser`, and optionally `url`; protocol §9.1 without the token fields) for a step only a human can take. `url` names the page where the person takes the step; it is omitted when the step is taken inside the application itself (a menu, a dialog) and no page names it. An application MUST NOT invent a `url`. A handoff without one is reported ([S-ACT-4], [S-AXE-8]) and never becomes `needs_human` ([S-AXE-2]).

**[S-AV-4]** Availability text (`name`, `reason`, `instructions`, `whatAgentShouldSayToUser`) is agent-read text and is subject to protocol §18.

## 5. Observe and act

**[S-OBS-1]** `observe()` returns `{ protocol, app, profile?, rev, at, entries, objects, ledgerSeq }`. `profile`, when configured, is structured live application data: `{ id, name, description?, context?: { kind, id?, name? }, authentication?: { state } }`, where `state` is `unknown`, `signed-out`, or `signed-in`. It contains no connection configuration or agent-instruction field. `id` is stable and `app` uses the profile name for compatibility. Each entry row carries `index`, `id`, `kind`, `role`, `name`, `object`, `rev`, and its kind's members. `index` is a 1-based position among rows that can be acted on now, and `null` otherwise. `ledgerSeq` is the latest ledger sequence number (§5.1).

**[S-OBS-2]** Unavailable actions, read-only fields, and collections that cannot load more remain in `entries` with their reasons. Agents learn why not before attempting.

**[S-OBS-3]** Three reads serve consumers that derive something per entry without taking a whole observation. `entries()` returns the registered entries in registration order. `registryVersion()` is a counter that moves on every `register`, `unregister`, `reconcile`, and `reset`, and on nothing else: a `bump` alone leaves it, so a consumer can tell "the table changed shape" from "the revision moved". `availability(id)` returns one entry's live availability as `observe()` would report it: an action's `state` with `requires` as `accepts` entries, a field's read-only `reason`, `cannot load more` for a collection without `more`, and the freeze's reason for every kind while frozen ([S-FRZ-1]); undefined for an unknown id.

**[S-OBS-4]** `subscribe(listener)` calls the listener, with no argument, after every change to what `observe()`, `availability()`, or `attributesFor()` can report: a `register`, an `unregister` or `reconcile` that removed a row, a `bump`, a `setRev`, a `seedRev` that adopted a revision, a changed `profile` through `configure` or `setProfile`, a `freeze`, a `thaw`, and a `reset`. It returns the function that unsubscribes. It is the subscribe function React's useSyncExternalStore takes, and it fires in `app` revision mode, where no `bump` happens. `onChange` keeps its narrower meaning ([S-FRZ-2]): it fires on `bump`, `freeze`, and `thaw` and not on registration, so a consumer that rebuilds per change of the action set (the bridge's `onChange`, and the MCP tool-list notification behind it) is not woken once per registered row.

**[S-OBS-5] Filtered, paged observation through the bridge.** `<ns>.observe` ([S-AXE-1]) takes an input of optional members: `object` (rows whose `object` equals it), `kind`, `available` (`true`: rows with an `index`; `false`: rows without), `query` (rows whose `name`, `id`, or `object` contains it, case-insensitively), `limit`, and `cursor`. Its output is the observation of [S-OBS-1] with `entries` narrowed to one page of the matching rows, plus `total` (the number of matching rows) and `nextCursor` (present exactly when more rows match). Rows keep registration order ([S-ENT-5]) and carry the `index` and `rev` they have in the whole observation, so an index read from a filtered page still resolves under [S-ACT-7]. The action declares `pagination` (protocol [P-AFF-7]) with `cursorIn` `/cursor`, `cursorOut` `/nextCursor`, and the bridge's page size: `limit` defaults to `pageSize` and MUST NOT exceed `maxPageSize` (a larger `limit` is `invalid_input`). Defaults: 1000 and 1000 for `surfaceActions`, so a surface of up to 1000 rows is one page as before; 50 and 200 for `domainActions`. A cursor is valid only with the filters it was issued for (otherwise `invalid_input` at `/cursor`) and names the last row it returned and the row after it: the next page starts after the first of those still registered, else at the position after the page. Each page is an observation at its own `rev`; an act presents the `rev` of the page it read. `surface.observe()` is unchanged and returns every row.

**[S-ACT-1]** `act({ op, target, text?, expectedRev, actor?, confirm? })` returns an AXE result envelope. On success it returns `ok` with `{ rev, id, actor, changed, seq }`, where `changed` lists the entry ids whose state the act moved and `seq` is the ledger entry the act wrote (§5.1). A handler, a field's `set`, or a collection's `more` MAY return (or resolve to) `{ changed?, rev?, conflict? }`: `changed` is then what the handler reported, and `rev` is the application's revision after the change, adopted as `setRev` adopts it before the result is built unless it is older than the surface's ([S-REV-6]); `conflict` is a refusal ([S-ACT-11]). When the handler reports no `changed`, `changed` is `[id]` if the revision moved during the act (by the handler, or by a reported `rev`) and `[]` otherwise. An application whose revision arrives after the handler (a server revision adopted later with `setRev`) therefore reports `changed` and `rev` from the handler or accepts an empty `changed`; agents SHOULD re-observe rather than read `changed` as the whole story.

**[S-ACT-2]** When `expectedRev` differs from the current revision, `act` MUST return `error` with `code: "conflict"`, `retryable: true`, and `details: { expectedRev, currentRev, seq }` (the protocol's stale shape, [P-LIVE-3], plus the ledger `seq` of the refusal), and MUST apply nothing.

**[S-ACT-3]** A missing `expectedRev`, an unknown `op`, an `op` that does not fit the entry's kind, a `confirm` that is required and absent, text longer than `maxLength`, or text that fails the field's schema is `invalid_input` with `details.issues`. An unknown `target` is `not_found`.

**[S-ACT-4]** An unavailable action or a read-only field is `error` with `code: "unavailable"` and `details.reason`; when the entry declares `requires` or `handoff`, those are included in `details`, the handoff with or without its `url` ([S-AV-3]).

**[S-ACT-5]** `target` is an entry id or an index from an observation at the same revision. Ids are stable and SHOULD be preferred.

**[S-ACT-6]** `target` MUST be a non-empty string (an id) or a non-negative integer (an index). Any other value, including a missing or `null` target, an empty string, a negative or fractional number, `NaN`, a boolean, or an object, is `invalid_input` with an issue at `/target`, and no handler runs.

**[S-ACT-7]** An index MUST resolve only to the entry whose `index` in the observation at `expectedRev` is that number. An entry whose `index` is `null` MUST NOT be reachable by number, whatever position it holds in the table; a number that no entry carries is `not_found`. The revision guard of [S-ACT-2] MUST run before the target is resolved, so an index observed at an older revision is `conflict` and can never land on the row that slid into its slot.

**[S-ACT-8]** A string `target` that names a registered entry which cannot be acted on (an unavailable action, a read-only field, a collection that cannot load more) is `unavailable` with `details.reason` per [S-ACT-4], not `not_found`. `not_found` is reserved for a target no entry carries.

**[S-ACT-9] Ordering.** The acts on one surface run one at a time, in the order `act` was called. Every check of §5 that precedes the handler ([S-ACT-2] to [S-ACT-8], [S-FRZ-3]) runs when `act` is called (the claim), so a refusal never waits. An act that passes them while another act is in flight waits for every act claimed before it and, when it reaches execution, MUST run those checks again against the state at that moment: a revision moved by a predecessor's commit or by a person (`bump`, `setRev`) is `conflict`, a freeze taken while it waited is `unavailable`, and a control that became unavailable is `unavailable`; no handler runs. `expectedRev` keeps its meaning: it must equal the revision when the act executes, so a second act presenting the revision a predecessor has since moved is `conflict` ([S-REV-2]). An act on an idle surface starts its handler within the call. Reads do not wait: `observe()`, `availability()`, and `ledger()` answer at once and report the state before a handler in flight has committed. A handler that never settles holds back every later act; a handler MUST NOT await an `act` on its own surface, which would wait for itself.

**[S-ACT-10] A commit that leaves the revision in place.** When an app-owned revision arrives after the handler (the handler reports no `rev`), a commit does not move the revision the next act is checked against. So that two acts from one observation still cannot both commit, an act that commits closes every claim taken before it at the same revision, unless it provably changed nothing: the revision did not move and either the handler reported `changed: []` or the revision is surface-owned (where a change would have bumped it). A waiting act whose claim was closed is `conflict` with `details: { expectedRev, currentRev }` (equal values) and a message that the application has not reported its new revision. A handler that threw closes the claims too, since it may have written. An act claimed after the commit, at the same revision, is accepted: the agent that observes again is never refused for a revision that cannot move.

**[S-ACT-11] The application's own precondition.** The surface's checks guard one surface; two instances (two tabs, two clients) of one application pass their own checks at the same revision. For state that lives on a server, the write itself is the gate. `act` passes the handler, the field's `set`, and the collection's `more` an `ActContext` `{ id, op, expectedRev, actor }` as the last argument, `expectedRev` being the revision the act presented, which equals the surface's revision when the handler starts; the handler carries it into its transaction or conditional write (`UPDATE ... WHERE revision = $expectedRev`). A handler whose write fails its precondition refuses by returning `{ conflict: { currentRev? } }` (the `conflict` member of `HandlerReport`) or throwing a `SurfaceConflict` (exported by `@summationai/axe-surface`, with an optional `currentRev`). `act` MUST then return `error` `conflict`, `retryable: true`, with `details: { expectedRev, currentRev, seq }` (`currentRev` as the handler reported it, else the surface's revision), record a refusal ([S-LED-4]), and adopt nothing from the report: no `rev`, no `changed`. The application's newer revision reaches the surface the way every revision does, through `setRev` on its next refresh. A handler that refuses MUST have written nothing.

**[S-REV-1]** The revision has one owner at a time, the surface's revision mode. In `surface` mode the application's state lives in the browser and it calls `bump()` after every change an agent could observe, whoever made it. In `app` mode the application has a revision of its own (a server counter) and adopts it with `setRev()`; the surface's stale check is then the first of two, and the server refuses a stale expected revision again, in the write itself ([S-ACT-11]). Unless pinned by `createSurface({ revision: "surface" | "app" })`, the mode follows the last call: `bump()` makes it `surface`, `setRev()` makes it `app`, and a fresh surface is `surface`; `seedRev()` leaves it alone. `revisionMode()` reports it. Freezes ([S-FRZ-2]) are the one behavior that differs by mode.

**[S-REV-2]** A retried act with the same `expectedRev` after a successful act MUST be refused (the revision moved), so a lost response cannot double-apply.

**[S-REV-3]** An act by one participant is visible to every other participant as a revision move; a human's change between an agent's observe and act is caught by [S-ACT-2].

**[S-REV-6] A stale report.** A `rev` a handler reports that is lower than the surface's revision when the handler settles (a newer revision arrived with `setRev` or `bump` while it ran) MUST NOT be adopted: the act is still `ok`, `output.rev` is the surface's current revision, `changed` is as reported, and the ledger entry carries the report as `ignoredRev`. A surface revision is an integer, so "lower" is well defined here; the protocol's revision stays opaque to agents ([P-LIVE-10]). Acts on one surface cannot complete out of order ([S-ACT-9]), so a stale report comes from a change made outside `act`.

**[S-REV-4]** Every act and every refusal is recorded in the surface's ledger (§5.1), so every change names who made it and at which revision, and every attempt that changed nothing says so.

### 5.1 The ledger

The first Surface left the record of who acted to the application, and its own critique was that the person never sees the agent's work: no ledger, no attribution, no replay. The surface is the one place every act passes through with the actor and both revisions in hand, so it keeps the record.

**[S-LED-1]** A surface MUST keep a ledger. Every call to `act` MUST append exactly one entry, whether the handler ran, the handler threw, or the act was refused. The ledger holds three things and nothing else: the entries `act` wrote; the changes and refusals the application appended with `record` ([S-LED-8]); and, served through the bridge, the refusals the AXE runtime made before the bridge's handler ran, for a caller it admitted ([S-AXE-14]). An entry is `{ seq, at, op, target, actor, revBefore, revAfter, status, text?, textHash?, changed, ignoredRev?, source?, expectedRev? }`: `at` is when it was written; `op` is the op as requested; `target` is the entry id the act resolved to, or the target as requested when it did not resolve; `text` is present when the request carried it and the surface's text policy keeps it ([S-PRV-2]), and `textHash` in its place under the `hash` policy; `ignoredRev` is present when the handler reported a revision the surface did not adopt ([S-REV-6]); `source` is present only on an entry `act` did not write (`application` for `record`, `server` for a refusal the bridge recorded), so an entry `act` wrote has exactly the members it had before v0.9; `expectedRev` is the revision a caller refused before the surface presented. So that the ledger is a complete record of agent attempts, the checks of [S-ACT-3] that are the surface's own (`maxLength`, the field's schema, a required `confirm`) MUST run in the surface and not be duplicated in front of it: the bridge's input schemas describe the shape only ([S-AXE-6]). A request the runtime refuses before the surface for a caller it did not admit (no credentials for a protected action, a site key outside its allowlist, [S-AUTH-3]), or before it knew which action or caller it served (a malformed envelope, an oversized body), is not in the ledger; it is in the server's request events.

**[S-LED-2]** `seq` starts at 1 and increases by one per entry; a `seq` is never reused, including after entries are dropped ([S-LED-6]). `ledger()` returns entries oldest first. `ledger({ since })` returns the entries whose `seq` is greater than `since`, so an agent that observed `ledgerSeq` can ask what happened after it looked. `actor` filters to one actor. `limit` caps the count: the oldest `limit` entries after `since` when `since` is given, so a reader can page forward, otherwise the newest `limit`.

**[S-LED-3]** `actor` is the actor the request carried (default `agent`; through AXE, [S-AXE-3]), recorded for refusals as much as for acts that ran, and it is the same value the handler received. The surface MUST NOT substitute its own idea of who acted.

**[S-LED-4]** A refusal MUST be recorded as a refusal: `status` is the error code the act returned (`conflict`, `not_found`, `invalid_input`, `unavailable`), `changed` is empty, and `revAfter` equals `revBefore`. A handler that threw is recorded with `status: "internal"` before the error propagates. A ledger MUST NOT present a refusal as a change, and MUST NOT omit it: an agent that was refused at rev 9 after observing rev 7 did nothing, and the record has to say so rather than leave a gap.

**[S-LED-5]** `revBefore` is the revision when the act was last checked (at execution for an act that waited, [S-ACT-9]; when it arrived otherwise) and `revAfter` the revision when the entry was written, after the handler ran and any `rev` it reported was adopted; `changed` is as in [S-ACT-1]. In `app` mode a handler that reports nothing leaves `revAfter` equal to `revBefore` and `changed` empty, since the application's revision arrives later; the record is still true. `status` is `ok` only when the handler ran and returned. Every act result carries the `seq` of its entry: `output.seq` for `ok`, `error.details.seq` for a refusal.

**[S-LED-6]** Retention MAY be bounded, and is by default: the surface keeps the most recent 1000 entries (`createSurface({ ledger: { max } })`). Dropping old entries MUST NOT renumber the rest, and `ledgerSeq` still reports the latest `seq`. The ledger is the application's live record, in memory; a durable audit trail is fed from the action events on the bridge ([S-AXE-5]) or by the application.

**[S-LED-7]** A change made through the application's own controls, outside `act`, appears in the ledger only when the application routes it through `act` or records it with `record` ([S-LED-8]); otherwise it is a revision move ([S-REV-3]) with no entry. An application that serves its surface to agents SHOULD record every change it makes outside `act` that moves the revision, so that an agent reading the ledger finds an entry for every revision it did not move itself.

**[S-LED-8] Recorded changes.** `record({ op, target, actor, changed?, text?, revBefore?, status?, expectedRev?, source? })` appends one entry and returns it. It MUST NOT run a handler and MUST NOT move the revision: the application makes its change and moves the revision itself (`bump`, `setRev`), and records it after. For a change (`status` absent or `ok`), `revBefore` is the value given (the revision the application read before its change, so the entry spans the move) or else the revision when `record` is called, and `revAfter` is the revision when it is called. For a refusal the surface never saw (`status` an error code), `changed` MUST be empty, and `revBefore` and `revAfter` are both the current revision ([S-LED-4]). `op` is the application's own word for what happened (`APPROVE`) and is not limited to the ops of `act`; `actor` is who did it, as the application attributes it. The entry takes the next `seq`, carries `source` (default `application`), and is subject to the text policy and the sensitive rule exactly as an act's entry is ([S-PRV-2]). `record` validates its argument and throws on a missing `op` or `actor`, an unknown `status`, or a refusal that names changed entries.

**[S-REV-5]** The application MUST re-register (or `reconcile`) whenever anything that feeds an entry's `state`, `value`, or `edit` changes, including transient states: a save in flight, data loading, a modal open. An observation MUST reflect the application's state as of its `rev`. A surface that reports a control available while the application has disabled it is a defect; §5.1 is the shortest way to avoid it for a state that spans the surface.

### 5.2 Transient states

**[S-FRZ-1]** `freeze(reason)` marks the whole surface unavailable for a transient state and returns `thaw`. While frozen, every action reports `{ available: false, reason }` with the freeze's reason in place of its own state (and no `requires` or `handoff`), every field is read-only with that `reason`, no collection can load more, and no entry carries an `index`. Field values remain visible.

**[S-FRZ-2]** `observe()` carries a top-level `frozen: { reason }` while frozen and omits it otherwise, and `freeze` and `thaw` each notify `onChange` listeners (with `frozen` or `thawed` naming the reason). Whether the revision moves depends on the revision mode ([S-REV-1]). In `surface` mode `freeze` moves the revision and so does `thaw`: the freeze is a change of the state the surface counts. In `app` mode neither moves it: the revision is the application's, a freeze is not a change of the application's state, and a counter the surface moved on its own would drift ahead of the application's until its next `setRev`, refusing agents for a change that never happened. `registryVersion()` moves in neither mode.

**[S-FRZ-3]** An act during a freeze is `error` with `code: "unavailable"`, `retryable: true`, and `details.reason` (also `details.frozen`), whatever the entry's own state, and no handler runs. A numeric target during a freeze is `not_found`, since no row carries an index. An act planned before the freeze (its `expectedRev` observed before it) is, in `surface` mode, `conflict` under [S-ACT-2] both during and after the freeze, because the revision moved; in `app` mode it is `unavailable` while frozen and, after the thaw, accepted exactly when the application's revision did not move in between, and `conflict` when it did. In both modes an act planned during the freeze is `unavailable` until the thaw.

**[S-FRZ-4]** Freezes nest and are counted: the newest reason is the one reported, the surface thaws when the last freeze is released, and releasing the same freeze twice does nothing.

## 6. The seam: every control as an AXE action

The reviewer who designed Surface put it in one line: each available Surface entry can be published as an AXE action, so discovery, MCP, kinds, and the audit come for free. An agent reading the manifest or an MCP tool list sees "Draft Jahmyr Gibbs (RB)" and "Lock March", each with its own availability and reason, not one `act` tool with a `target` parameter. The first cut of this seam had that generic action; it is gone. A second granularity, a fixed set of parameterized actions the application declares ([S-AXE-10]), serves surfaces too large or too changeable for a tool per control; it shares the act, the revision, the ladder, the ledger, and the events, and it is not the generic action of v0.2: each action covers a declared group with metadata true of every member.

**[S-AXE-1]** `surfaceActions(surface, { namespace })` returns an action provider (the SDK's `ActionProvider`, registered with `addProvider`) whose set is, in order: `<ns>.observe` (read-only, `risk: none`, filtered and paged per [S-OBS-5], `display` over `entries`, and a dynamic affordance per actionable row that names the row's own action with `input: {}` and the observation's `rev` as the affordance's `expectedRev`), `<ns>.ledger` (read-only, `risk: none`, input `{ since?, limit? }`, output `{ ledgerSeq, entries }` with `display` over the entries), and one action per registered entry ([S-AXE-6]), in registration order. Contract v0.2's generic `<ns>.act` is removed; its `target`, `op`, and `input.expectedRev` have no successor, since each action names its entry and op and the revision travels on the envelope ([S-AXE-4]).

**[S-AXE-2]** Refusals map onto the ladder: an unavailable action with `requires` becomes `needs_input` with those `accepts` (and the declared `handoff` as `fallback` when it has a `url`); one with only a `handoff` that has a `url` becomes `needs_human`; a stale revision is `error` `conflict`; other refusals stay `error` with their reason. A `handoff` without a `url` ([S-AV-3]) never climbs the ladder, because `needs_human` requires a complete Handoff to resume from ([P-HAND-1]): the act stays `error` `unavailable` with `details.handoff` carrying the `reason`, `instructions`, and `whatAgentShouldSayToUser`, so the agent still learns what would unblock it. A refusal during a freeze ([S-FRZ-3]) is `error` `unavailable` with the freeze's reason and never climbs the ladder, since there is nothing to fulfill or hand off until the freeze lifts. On `/axe/continue`, the application's `fulfill` runs and the act is retried at the current revision; on `/axe/resume`, the act is retried at the current revision. The `state` a continuation or resume carries is the act request, with the entry id as `target`, so a later act lands on the same control whatever the action set has become.

**[S-AXE-3]** The `actor` recorded for an act that arrives through AXE is the authenticated `onBehalfOf` when there is one, else `agent`.

**[S-AXE-4]** Served through AXE, the surface's revision is the site's revision (protocol §21): the server is created with `revision: surface.currentRev`, so every envelope carries `rev`, the protocol's stale check ([P-LIVE-3]) runs before the handler, and `/axe/state` reports the revision. The revision the agent observed travels as the request envelope's `expectedRev` and nowhere else; an entry's action takes none in its `input`. The entry's action MUST pass the envelope's `expectedRev` to `act` unchanged. The protocol's check is the first gate and the surface's the second: two requests that pass the server's check at the same revision are ordered by [S-ACT-9], the later one re-checked at execution, so at most one of them commits when the first moves the revision; the handler then receives the same `expectedRev` for its own write ([S-ACT-11]). A request without `expectedRev` reaches the surface, which refuses it as `invalid_input` under [S-ACT-3]: every act presents the revision the agent saw.

**[S-AXE-5]** For every act that goes through an entry's action, `/axe/continue`, or `/axe/resume`, run or refused, the bridge MUST emit one action event (`EVENTS.md`, "Action events") named `surface.act`, with `action` the entry's action name, `status` and `errorCode` as the surface returned them, `actor` as recorded in the ledger, and `details: { seq, op, target, revBefore, revAfter, changed }`. Action events reach the server's `onActionEvent` sinks, not its analytics sinks, because they name the actor.

**[S-AXE-6] The action for an entry.** Its `title` is the entry `name` ([S-ENT-1]: the outcome, in the application's words). Its `description` is composed from the kind, the name, the `object`, and the effect, and stays within [P-ACT-7]'s bounds whatever the name's length; it does not carry the availability, which is live ([S-AXE-8]). `readOnly` is false for every kind: an action runs a handler, a field runs a setter, and a collection load changes the view. The `input` describes the shape of a request and nothing the surface checks itself, so every refusal of [S-ACT-3] is the surface's and is ledgered ([S-LED-1]). For an `action` entry, `idempotent`, `reversible`, and `risk` are the `effect`'s ([S-EFF-1]); `input` takes an optional boolean `confirm`, described as required to be `true`, when the effect declares `confirm`, and an optional `text` described by the effect's `text` prompt when it declares one. For a `field` entry, `idempotent` is true (setting the same text twice sets it once), `reversible` and `risk` are the bridge's field options (defaults false and `medium`), and `input` is `{ text }`, required, a string; the `maxLength` is named in its description and in the action's `description`, and `<ns>.observe` carries `edit.maxLength` and `edit.schema`. A read-only field keeps the same shape and is unavailable ([S-AXE-8]). For a `collection` entry that can load more, `idempotent` and `reversible` are false, `risk` is `low`, and `input` is empty; a collection without `more` has no action at all, since there is nothing to invoke, and keeps its row in `<ns>.observe` ([S-OBS-2]). Every entry action's `output` is the act output of [S-ACT-1]: `{ rev, id, actor, changed, seq }`. An action entry that declares a `handoff` with a `url` at registration declares `humanHandoff: { reasons: [handoff.reason] }`. The op the action performs is fixed by the entry: `TOGGLE` for a `switch`, `CLICK` for any other action role, `TYPE_TEXT` for a field, `SCROLL_DOWN` for a collection.

**[S-AXE-7] Names.** An entry's action is `<ns>.<slug>`. The plain slug of an id is the id lowercased, with every run of characters outside `a-z0-9` replaced by one hyphen, leading and trailing hyphens dropped, and `e-` prefixed when the result is empty or starts with a digit, so `pick:me:Gibbs` is `pick-me-gibbs`, `cell:2026-03` is `cell-2026-03`, and `2026-03` is `e-2026-03`. When the plain slug is `observe`, `ledger`, or `act`, or is already held by a different id, the slug is the plain slug, a hyphen, and a short hash of the exact id (FNV-1a, base 36), with a counter appended in the vanishing case of a second collision. The bridge keeps the map in both directions for its lifetime: `actionNameFor(entryId)` always returns the same name for the same id, an id that leaves and returns keeps its name, and `entryIdFor(actionName)` returns the exact id an action was issued for, or undefined for a name the bridge never issued. `entrySlug(id)` exposes the plain slug alone. Every name produced fits [P-ACT-1]'s pattern.

**[S-AXE-8] Availability.** Every entry action declares an `availability` hook ([P-LIVE-5]) that returns `surface.availability(id)` ([S-OBS-3]): an action's `state` with its `reason`, `requires`, and `handoff` (with or without a `url`); `{ available: false, reason }` for a read-only field; and, while the surface is frozen, `{ available: false, reason }` with the freeze's reason for every entry ([S-FRZ-1]). The manifest carries it as rendered and `/axe/state` serves it live, so an agent sees per control what it can do right now and why not the rest without calling `<ns>.observe`. The hook reads one entry; it MUST NOT take a whole observation, so `/axe/state` over hundreds of rows costs hundreds of lookups, not hundreds of tables.

**[S-AXE-9] Churn and scale.** The action set follows the registry: an entry registered or unregistered is in or out of the manifest, `/axe/state`, and the derived MCP tool list on the next request, without re-registering anything with the server. The set is rebuilt only when `registryVersion()` moved; a `bump` alone reuses the previous set, and within a rebuild an entry object already published keeps its action. Name lookup on invocation is by map, not by scan, so a surface with hundreds of rows invokes in constant time. An entry whose text fails the honesty lint ([P-HON-1]) at build time is not published as an action: the bridge reports it through its `onError` option (default: one warning per entry) and the entry keeps its row in `<ns>.observe`, without an affordance. A retried `idempotencyKey` for an action whose entry has since left the registry (a pick that leaves the board when drafted) is answered from the idempotency store by the server before the name is declared unknown ([P-IDEM-2]), so a lost response is still recoverable.

**[S-AXE-10] Parameterized domain actions.** `domainActions(surface, { namespace, domains })` returns an action provider whose set is, in order, `<ns>.observe`, `<ns>.ledger` (as in [S-AXE-1]), and one action per declared spec, named `<ns>.<spec name>`. The set is fixed when the provider is created: it does not change as entries register and unregister, and the provider's `onChange` never fires. Each spec carries a `title`, a `description`, `covers(entry)`, and `risk`, `idempotent`, `reversible`, and optionally `auth` and `humanHandoff`. An entry belongs to the first spec whose `covers` returns true, decided once per registered entry object, subject to [S-AXE-11]. Without `domains` the specs are `set-field` (fields; the bridge's field risk, idempotent), `run-control` (action entries; `risk: high`, not idempotent, not reversible), and `load-more` (collections; `risk: low`). The action's input is `{ entryId, text?, confirm? }`, `entryId` a non-empty string; its output is the act output of [S-ACT-1]. The act it performs is `surface.act` with `target` the `entryId`, the op the entry's own action would use ([S-AXE-6]), the envelope's `expectedRev` unchanged ([S-AXE-4]), and the actor of [S-AXE-3]; refusals map onto the ladder as in [S-AXE-2], with the saved act's `target` the entry id, and every act emits the event of [S-AXE-5] with `action` the domain action's name. So the revision, the ledger, and the events are the same in both granularities for the same act. `<ns>.observe` gives every actionable row whose entry is covered an affordance naming the covering action, with `input: { entryId }` and the observation's `rev` as `expectedRev`. `actionFor(entryId)` returns the covering action's name and `covered(name)` the covered ids.

**[S-AXE-11] Metadata true of every covered entry.** A spec's `risk`, `idempotent`, and `reversible` are published for the whole group, so they MUST hold for each entry it covers ([P-HON-7]). An entry whose own risk ([S-AXE-6]) is higher than the spec's, that is not reversible while the spec is declared reversible, or not idempotent while the spec is declared idempotent, is not covered. Neither is an entry whose `name` or effect `text` fails the honesty lint ([P-HON-1]). Such an entry is reported once per entry object through `onError`, keeps its row in `<ns>.observe`, and has no affordance; an act naming it through a domain action is refused under [S-AXE-12].

**[S-AXE-12] Routing and availability of a parameterized action.** An `entryId` that names a registered entry covered by a different spec, or by none, is `invalid_input` at `/entryId` before the surface, as an unknown action name would be, and is not ledgered; so is a field entry without `text` (the per-control action's schema requires it). An `entryId` no entry carries goes to `act`, which refuses it as `not_found` and records it ([S-LED-1]). The action's `availability` hook ([P-LIVE-5]) reads one entry at a time and never a whole observation: `{ available: true }` while at least one covered entry can be acted on ([S-OBS-3]); otherwise `{ available: false, reason }` with the reason every covered entry reports when they all report the same one (a freeze, [S-FRZ-1]), else the spec's `idleReason`. [S-AUTH-5] applies unchanged: for a caller the runtime has not identified, a protected action reports `{ available: true }` without reading a surface. Per-entry availability, `requires`, and `handoff` are reported on the entry's row of `<ns>.observe` and in the refusal of an act on it, as for its own action.

**[S-AXE-13] Both granularities side by side.** `surfaceActions` and `domainActions` MAY serve the same surface on one server under different namespaces; their acts share the surface's revision, act ordering ([S-ACT-9]), and ledger. Per-control names are stable per entry id for the life of a bridge ([S-AXE-7]); domain action names are the application's and do not depend on entries. Resolvers and templates ([S-AUTH-4]) work the same way in both; with a resolver the coverage of an entry is decided on the caller's own surface.

**[S-AXE-14] Refusals before the surface.** An action provider MAY declare `onResult(ctx, result)`; the server calls it for every result of an action that provider supplied, on every endpoint, after the site's own `onResult`, with the hook context plus the `identity` and `siteKey` the runtime established, the envelope's `input` and `expectedRev` on the action endpoint, and `handled`, true when a handler (or `onContinue`, `onResume`, `onPoll`, or the replay of one) produced the result. Both bridges declare it, so `addProvider` wires it. On the action endpoint, for a result of one of the bridge's acting actions (not `<ns>.observe` or `<ns>.ledger`) that is an `error`, was not `handled`, and carries no `details.seq`, the bridge MUST record the refusal on the caller's surface with `record` ([S-LED-8]): `source: "server"`, `status` the error code, `target` the entry id (per control, the id the action name was issued for, [S-AXE-7]; for a domain action, the input's `entryId` when it is a non-empty string, else the action name), `op` the op that entry's own action performs ([S-AXE-6]; `CLICK` for an id no entry carries), `actor` as [S-AXE-3] would have recorded it, the input's `text` when it is a string (subject to [S-PRV-2]), and the presented `expectedRev` when it is a number. It records only for a caller the runtime admitted under the action's `auth` mode: any caller for `none`, an authenticated user for `user`, a verified site key for `site`; an unadmitted caller writes nothing to a protected surface's ledger ([S-AUTH-3]). A public (`none`) action records an anonymous caller's refusal as `agent`, as it records that caller's acts. With a resolver, the caller's surface is resolved from the same context; a caller with no surface writes nothing. It MUST NOT record a result more than once per request, and emits no action event (the server's request events already carry the refusal). So a stale `expectedRev` refused by the protocol's first gate ([S-AXE-4]) is in the ledger once, as `conflict`, and a refusal the surface made is in it once, from `act`. A refusal of `/axe/continue` or `/axe/resume` before its handler, and a routing refusal the domain action's handler makes itself ([S-AXE-12]), are not recorded.

### 6.1 Authorization and privacy

A surface holds field values, domain objects, and the free text agents typed. In the browser that is the page's own data ([S-DOM-2]); served over HTTP it is published to whoever can reach the server. The rules below make the second an explicit decision. They do not change [S-RULE-1]: the surface still decides nothing about who may do what inside the application; the bridge declares which callers the AXE runtime lets through at all, and the runtime enforces it (protocol §16).

**[S-AUTH-1] The bridge declares who may call.** Every action `surfaceActions` generates carries an `auth` mode (protocol [P-AUTH-1]), from the `auth` option: `user` (the default), `site`, or `none`. A server rejects an action whose mode is not in its `auth.modes`, so a server that lists no `user` mode, including one created with the protocol's public default `{ modes: ["none"] }`, refuses a bridge created without options on its first request instead of serving it. `auth: "none"` is the only way to make a surface public over HTTP, and it is written by the integrator. A mode outside the three is an error when the bridge is created.

**[S-AUTH-2] Read and mutate.** The `read` option sets the mode of `<ns>.observe` and `<ns>.ledger` (default: `auth`). `authFor(entry)` sets one entry's action's mode, and returns undefined to keep `auth`. A public read side over protected controls (`read: "none"`) publishes every value `observe` returns; it is a choice, not a default.

**[S-AUTH-3] Authorization is the runtime's refusal, never a reason.** A caller the runtime cannot admit is refused by the runtime before any bridge handler runs: `unauthorized` without credentials (or `needs_human` with `login_required` when a `user` action and a login page are configured, [P-AUTH-4]), `forbidden` for a site key outside its allowlist ([P-AUTH-2]). Nothing reaches the surface, the ledger, or the action events. An entry's `state.reason` stays the application's capability report; the bridge never writes an authorization message into it, and never answers an unauthorized caller with `unavailable`.

**[S-AUTH-4] One surface per caller.** A server that hosts the surfaces of many users or tenants passes a resolver, `(context) => Surface | null`, in place of the surface, with a `template` surface. The context is what the runtime established: `identity`, `tenant`, `siteKey`, `request`. The template's entries define the action set for every caller: the manifest, `/axe/state`, and the MCP tool list show the template's names and never the union of callers' entries, so no caller's names or ids reach another caller or an anonymous reader. Each request resolves the caller's surface once; `observe`, `ledger`, and every act run against it, an act on an id the caller's surface does not hold is `not_found` from that surface, and a caller's revision is its own surface's. A resolver that returns nothing refuses the call with `unauthorized` for an unidentified caller and `forbidden` for an identified one, saying nothing about other callers. `scopedSurfaces({ create, key?, max?, idleMs? })` builds a resolver whose default key is the tenant id and the principal (the user's `onBehalfOf`, else `site:<key id>`), creates a surface on a scope's first request, and evicts the least recently used surface beyond `max` (default 1000) and any surface idle longer than `idleMs` (default 30 minutes). With a resolver the server's `revision` option is not the surface's, since the protocol's revision provider does not see the caller: leave it off and the surface's own guard ([S-ACT-2]) checks `expectedRev`, or give a provider that resolves the caller itself.

**[S-AUTH-5] Anonymous views read nothing protected.** The manifest's `availability` is computed for an anonymous caller ([P-LIVE-7]) and `/axe/state` for the caller who asks. For an entry whose mode is not `none`, the bridge's availability hook returns `{ available: true }` without reading any surface when the runtime established no identity: the protocol's report for an action that declares no availability, meaning the surface makes no claim to that caller, while `auth` says who may call. It reads the caller's surface once the caller is identified. A `site` caller without a user identity is unidentified here, since the availability context carries no site key.

**[S-AUTH-6] Actor and principal.** The recorded `actor` is still [S-AXE-3]'s; scoping is by principal and tenant, never by the actor string, which an application may map to a display name.

**[S-PRV-1] Sensitive fields.** A field entry MAY declare `sensitive: true`. Its row in `observe()` carries `sensitive: true` and no `value`, locally, through `expose`, and through `<ns>.observe`; `describeEntry` says `value hidden`; the DOM mirror never carries a value for any entry ([S-DOM-1]); the ledger keeps none of its text ([S-PRV-2]). The application's own `objects` are its responsibility: keep private data out of `setObjects` or protect the read side.

**[S-PRV-2] Ledger text policy.** `createSurface({ ledger: { text, redact } })`: `text` is `keep` (the default), `hash` (the entry carries `textHash`, the hex SHA-256 of the text, and no `text`), or `omit`. `redact(text, entryId)` rewrites kept text, and returning undefined drops it. The policy applies to every entry the ledger writes: acts that ran, refusals, and handlers that threw. A sensitive field's text is never kept under any policy, and neither is the text of an act whose target did not resolve to an entry while any sensitive entry is registered, since a refusal before resolution cannot say which row it meant. A hash links equal texts; it does not hide guessable text.

**[S-PRV-3] Action events.** A `surface.act` event ([S-AXE-5]) carries no text and no value. The bridge's `redactEvent(details, { action, entryId })` rewrites its `details` before emission, for run and refused acts alike, for ids that are themselves personal.

## 7. Browser agents

Browser-driving agents and screen readers read a control's accessible name, not its registration. Surface mirrors each entry onto the element that receives its interaction, so the page, `observe()`, and the screen reader all read the same outcome-stating name. Two of three gains in the first trial came from the names alone.

**[S-DOM-1] The DOM mirror.** The rules below hold for every entry that has a control on screen.

1. An entry's `name` states the outcome in the application's own words ("Draft Jahmyr Gibbs (RB)", "Lock March", "Load more players"). It MUST NOT name the widget ("button", "Draft button"), repeat the `role`, or carry the state ("disabled", "already drafted"): the role is `role`, the state is `state`. The same string is the control's accessible name and the `name` in `observe()`.
2. The element that receives the entry's interaction (the button, the input, the scrolling container) carries these attributes, and no other element in the document carries its `data-surface-id`:

   | Attribute             | Value                                    | When                                     |
   | --------------------- | ---------------------------------------- | ---------------------------------------- |
   | `aria-label`          | the entry `name`                         | always                                   |
   | `data-surface-id`     | the entry `id`                           | always; exactly one element per entry    |
   | `data-surface-kind`   | `action`, `field`, or `collection`       | always                                   |
   | `data-surface-object` | the entry `object`                       | when the entry has one                   |
   | `aria-disabled`       | `true`                                   | an action whose `state` is not available |
   | `aria-readonly`       | `true`                                   | a read-only field                        |
   | `data-surface-reason` | the `reason`, in the application's words | with `aria-disabled` or `aria-readonly`  |

   Collections carry the common set only.

3. Two helpers produce that set. `surfaceAttributes(entry)` returns it as strings from a registered entry or an observed row, read from the entry alone: it reports the entry's own `state` and `edit` and knows nothing of a freeze, and it returns only what to set. `surface.attributesFor(id)` returns `{ set, remove }` for a registered entry from its live availability ([S-OBS-3]): during a freeze `set` carries `aria-disabled` or `aria-readonly` with the freeze's reason, and `remove` lists every attribute of `SURFACE_ATTRIBUTES` (the table above, exported from `@summationai/axe-surface`) that is not in `set`, so a renderer that applies both never leaves the previous render's reason on a control that became available. `remove` never names `aria-label` or `data-surface-id` for a registered entry, since both are always in `set`, so a renderer that keeps its own `aria-label` need only skip setting it. An application that re-renders controls while the surface lives MUST use `attributesFor` or an equivalent that reads `availability(id)`; `surfaceAttributes` is for a one-time render. `useSurfaceProps(entry, deps)` (`@summationai/axe-surface/react`) registers the entry like `useSurface` and returns the live set as props, with `aria-disabled` and `aria-readonly` as booleans, re-rendering when it changes (it reads the surface through `subscribe` [S-OBS-4], so a change made outside the component, by another writer or by `reconcile`, reaches the control too). An application that uses any of these MUST render every attribute returned on that element, MUST remove the attributes named in `remove`, and MUST NOT replace `aria-label` or `data-surface-id` with other values. An application that renders by hand SHOULD carry the same set.
4. The mirror reports; it does not disable [S-RULE-1]. The helper sets `aria-disabled`, never `disabled`, so the application keeps its own disabling logic, and an `aria-disabled` control stays focusable, so a screen reader reaches the reason beside it.

**[S-DOM-2]** `expose(window)` publishes `observe`, `act`, `ledger`, and `rev` at `window.__surface` for agents that drive the page. This is browser-local: whatever runs in the page can already read what the page renders and call its handlers, so `expose` adds no reader the page did not have, and it needs no `auth`. It is not equivalent to serving the surface over HTTP, where §6.1 applies. `expose` returns the same `observe()` as the surface, so a sensitive field's value is withheld there too ([S-PRV-1]).

**[S-DOM-3] The selector contract.** `surfaceSelector(id)` returns `[data-surface-id="<id>"]` with the id as a double-quoted CSS string: backslashes and double quotes are escaped with a backslash, a newline becomes `\a `, and everything else (colons, spaces, dots, brackets) is left as it is. On a page that follows [S-DOM-1], `document.querySelector(surfaceSelector(row.id))` MUST return the control for `row.id` from any observation, whatever the id contains. Ids are stable [S-ACT-5], so a selector computed from one observation still finds the control after the revision moves; a stale selector is never an error, a stale act is [S-ACT-2].

**[S-DOM-4] One-line description.** `describeEntry(entry)` returns one line of plain text: the `name`, a colon, then the entry's availability in the application's words (`available`, or `unavailable, <reason>`; for a field `editable` or `read only, <reason>`, followed by its value and length; for a collection what is loaded and whether it can load more), and for an action a semicolon and its effect (`mutates <state>`, `idempotent` when set, `reversible` or `not reversible`, `risk <level>`, `confirm required` when set): "Draft Jahmyr Gibbs (RB): unavailable, already drafted by another team; mutates draft, reversible, risk medium". It is agent-read text [S-AV-4]. Applications MAY render it as `aria-description` on the control or log it beside each act; the helper does not render it by default.

## 8. WebMCP: the browser's own agent

WebMCP is a draft browser API (W3C Web Machine Learning Community Group, draft report of 17 September 2026) through which a page registers tools for an agent built into the browser: `document.modelContext.registerTool({ name, description, inputSchema, execute, annotations }, { signal })`, unregistered by aborting the signal. As of September 2026 Chrome offers it behind a flag and in an origin trial (from Chrome 149); other browsers do not ship it. `@summationai/axe-surface/webmcp` maps a surface onto it. It is optional and feature-detected; `SurfaceProvider` enables it with the `webMcp` prop, while framework-free pages import the subpath directly.

**[S-WEB-1] Feature detection and diagnosis.** `exposeWebMcp(surface, options)` registers nothing unless it finds an object with `registerTool` (by default `document.modelContext`), and then returns a handle with `supported: false` and the reason. Its `diagnostic()` distinguishes unavailable, registering, ready, degraded, registration error, and closed states and names each refused registration without exposing page data. The page, its controls, and `expose` ([S-DOM-2]) behave the same with or without WebMCP. The adapter reaches the browser API in one place, so a change in the draft changes that place only.

**[S-WEB-2] What is offered.** One tool reads the surface (`<prefix>observe`, read-only: the observation of [S-OBS-1] as text and as structured content, with the filters and pages of [S-OBS-5]: `query`, `kind`, `object`, `available`, `limit`, and `cursor`). When the surface carries the derived page-content reader of [S-AUTO-14] and [S-AUTO-15], `<prefix>read` returns that bounded, redacted content and `<prefix>wait` waits for one of its bounded conditions; both are read-only and may be disabled together with `content: false`. One tool per entry that can be acted on: an action, a field that is not `sensitive`, a collection with `more`. A sensitive field ([S-PRV-1]) gets no tool, and no tool description or result carries its value. The tool's description is `describeEntry` ([S-DOM-4]) plus what the tool does; its input schema is a JSON Schema object with an optional `expectedRev`, `text` for a field (with the field's schema and `maxLength`), and a required `confirm` for an action whose effect asks for confirmation. Every tool that acts states `consequentialHint`: `true` for an action that is not reversible, `false` otherwise, so an agent need not assume the worst of a tool that says nothing; an idempotent entry also carries `idempotentHint`. Tool names are the prefix (default `surface_`) and the id with every character outside letters, digits, `_`, and `-` replaced by `_`; ids that map to the same name, or to the observe, read, or wait tool's, get an 8-hex-digit hash of the id appended. Names are stable for an id.

**[S-WEB-3] Availability follows the surface.** The adapter follows `subscribe` ([S-OBS-4]) and re-registers a tool when its name, description, schema, or annotations changed, and only then. An unavailable entry is registered with its reason, `requires`, and `handoff` in the description (`unavailable: "describe"`, the default) or left out until it is available (`"omit"`). A freeze makes every entry unavailable with the freeze's reason ([S-FRZ-1]).

**[S-WEB-4] Acts go through the surface and approval is trusted.** A tool call is `surface.act` with the entry's id, the entry's op, the tool's `text` and `confirm`, and `expectedRev` from the call, or, when the call gives none, the surface's revision at the moment of the call. Before a high-risk action, an action that declares `confirm`, or an entry whose handoff reason is `approval_required`, the adapter requires a trusted approver: a host's ([S-WEB-6]) or else the application's `requestApproval` callback; without either it refuses and runs nothing. The callback is trusted application UI, receives the exact entry, act, and input, and must resolve only from the person's interaction. An approval opens an auto-surface gate for that exact entry and is recorded before the act; a denial runs nothing. The callback MUST NOT be reachable by an agent. The surface's revision guard, availability, confirmation, ledger, and handler otherwise apply unchanged ([S-ACT-2], [S-LED-1]); the ledger's `actor` is the adapter's (`webmcp` unless set). The result is the act's envelope as structured content with a line of text, and `isError` when it is not `ok`.

**[S-WEB-5] Browser-local and host-delivered.** Like `expose`, WebMCP exposure adds no reader the page did not have: the browser's agent acts in the page with the user's session. The browser host must both implement `document.modelContext.registerTool` and deliver registered tools to that agent task. A generic browser-automation or headless-computer-use session with only click/type primitives is not thereby a WebMCP host; its UI actions do not pass through `surface.act`. WebMCP is not a way to reach the surface from a server; server-side agents use the AXE bridge (§6) and its authorization (§6.1).

**[S-WEB-6] Host-delivered approval.** A host that runs the page for a person where no one sees it (a headless browser) MAY install an approver before any page script runs: a non-writable, non-configurable function at the global named by `INJECTED_APPROVER_GLOBAL`. The adapter uses it only when the property is so defined, and then in preference to `requestApproval`, whose UI no one would see. It passes plain data (the tool, the entry's id, name, application, risk, what it mutates, whether it is reversible, and the bound revision) and takes a decision, which is recorded before the act as under [S-WEB-4], or an unanswered result: nothing runs, no decision is recorded, and the call returns `unavailable` with reason `approval_pending`, retryable, with the host's message. The host MUST obtain the decision from the person through a channel the agent cannot answer (its MCP client's elicitation, or a page shown to the person), MUST bind a decision made outside the call to that entry at that revision and use it once, and MUST NOT put a link that decides into anything the agent receives.

**[S-WEB-7] Domain granularity.** With `granularity: "domain"`, the adapter registers, beside the observe tool (and read and wait, [S-WEB-2]), one tool per domain action ([S-AXE-10]) instead of one per entry: `<prefix><name>` for each spec, by default `domainActions`' own set, or on an auto surface `autoDomains()`'s entry actions (`navigate` first, so a link or landmark is offered as the low-risk navigation it is). Each takes the `entryId` of an observe row, and `text`, `confirm`, and `expectedRev` as the per-entry tool does. The first spec that covers an entry acts on it, and a spec covers an entry only when the entry's risk is no higher than the spec's and it is reversible or idempotent where the spec says so. A call for an entry that another tool acts on is refused with that tool's name, and one for an unknown or sensitive entry as `not_found`; nothing runs. The observe tool names each row's tool. Descriptions carry no row state, so the set is registered once and does not change with the page. Acts, approval ([S-WEB-4], [S-WEB-6]), the revision guard, and the ledger are those of the per-entry tools.

## 9. Execution modes

A surface runs in the JavaScript realm that created it. Two applications built with the same modules can therefore have two unrelated surfaces: the page's, in the browser, and the server's, in the process that serves AXE. The rules below say which is which. They describe what the SDK does and, as much, what it does not do.

**[S-MODE-1] Browser-local.** A surface created in a page, and the entries the page's components register on it (`useSurface`, `useSurfaceProps`, or `register`), belong to that page instance: one tab, one realm, for as long as the page and the registering components live. Their handlers are closures over that page's state and act with that page's credentials. They are reachable only by code in that realm: `expose(window)` ([S-DOM-2]) or an in-page adapter that holds the surface. Importing the same module on a server (a route handler, a server component) creates another surface in that process, empty, sharing no entry, revision, ledger, or session with any page.

**[S-MODE-2] Server-side.** A surface created in a server process, and hand-written AXE actions, live as long as that process. Served through `surfaceActions`, they are scoped by the runtime to the caller's principal and tenant ([S-AUTH-1] to [S-AUTH-4]). A server-side capability MUST NOT depend on a closure registered in a browser; the bridge serves only entries registered in its own process.

**[S-MODE-3] One broker, `@summationai/axe-relay`.** The SDK carries entries, acts, observations, and ledger entries between a page and anything outside it in exactly one way: `@summationai/axe-relay` (§9.1), which a page connects explicitly with `connectRelay` and which serves the page's surface to agents authenticated as the same person. Nothing else in the SDK carries them between a page and a server, between two tabs, or between two processes, and the relay never carries them between two principals. Any other connection an application builds (an in-page adapter an agent's host talks to) is the application's, with its scope and authorization the application's to state. State that several tabs, people, or agents share lives on the server and changes through server-side capabilities whose handlers write conditionally ([S-ACT-11]); a page surface in `app` revision mode adopts the server's revision ([S-REV-1]), so an agent in the page and an agent on the server present the same `expectedRev`.

**[S-MODE-4] Unmount and navigation.** Unmounting a component or leaving a page unregisters its browser-local entries ([S-ENT-5]); nothing on the server changes because of it. An act on an id that left is `not_found` from the page's surface ([S-ACT-3]), and the agent observes again.

### 9.1 The relay

`@summationai/axe-relay` lets an agent outside the browser act in a signed-in person's live tab. The page connects to a relay server (`connectRelay` from `@summationai/axe-relay/client`); the relay keeps a mirror of each connected tab's surface and serves it through `domainActions` ([S-AXE-10]) on an AXE server, derived to MCP by `@summationai/axe-mcp`, over Streamable HTTP or stdio (`createRelay` from `@summationai/axe-relay/server`, `axe relay`). A tab is attended (a person is looking at it) or unattended (a host runs it in a hidden browser session for the person, and the person approves in the agent's UI). The rules below are what the relay guarantees, and where it stops.

**[S-RELAY-1] The page decides.** An act an agent sends through the relay MUST run in the page as `surface.act`, so the page's act queue ([S-ACT-9]), revision check ([S-ACT-2]), availability ([S-ACT-4]), handler, and ledger decide it; the relay's own checks are the AXE runtime's revision check in front of it ([S-AXE-4]) and the gates of [S-RELAY-4] and [S-RELAY-9]. The mirror's `register`, `freeze`, `bump`, and `reset` throw: the page owns its entries. `<ns>.observe` and `<ns>.ledger` read the page's latest snapshot, and every surface tool call first asks the tab for a fresh one (served from the last snapshot when the tab does not answer within the relay's `syncTimeoutMs`).

**[S-RELAY-2] A tab is one person in one tenant.** A tab authenticates on its connection with a relay token the application's backend minted for the signed-in person, or through the relay's `authenticateTab`. A relay token is a JSON Web Token signed with HMAC-SHA256 whose `sub` is the principal, `org` the tenant, and `aud` the relay's audience (default `axe-relay`), with an `exp` at most one day after its issue; `mintRelayToken` and `verifyRelayToken` implement it. The page never sends its session cookie to the relay. The relay MUST refuse a connection whose `Origin` is not in its allowlist (exact origins, `https://*.<domain>`, `http://localhost:*`, or a function), a token it cannot verify, a revoked token, and a tenant outside `tenants`. A tab's record is keyed by its tenant, principal, and tab id; a new connection with a tab id another connection holds for the same person replaces it, and the replaced connection (a duplicated tab) takes a new id.

**[S-RELAY-3] An agent reaches only its own person's tabs.** An agent over HTTP authenticates with an OAuth access token (`agentAuth.verifier`), and `agentAuth.identify` names the principal and tenant it speaks for; a stdio relay acts for the principal it was started for; in development, an agent speaks for the principal of the tab it paired with ([S-RELAY-10]). The relay MUST serve an agent only the tabs whose principal and tenant equal the agent's: `relay_tabs` lists no other, `relay_select-tab` answers another person's tab id with `not_found`, and the surface tools resolve to no other. An agent with no tab gets an empty observation that says why.

**[S-RELAY-4] Lifetimes.** A connection lives no longer than its token: the page renews in-band (`getToken` before expiry) with a token for the same principal and tenant, and the relay closes a connection whose token lapsed or whose renewal names anyone else. Stop in the page, `relay_stop` from the agent, and `relay.stop` from the relay's owner each revoke the connection's token at the relay and mark the tab stopped; every later act on it MUST be `forbidden`, with nothing forwarded. `rekey` (a tenant switch or sign-in change without a reload) removes the tab's record and revokes its token before the page connects under the new identity, and drops a development pairing to a principal left with no tab. Leaving or reloading the page is not Stop: the relay keeps a disconnected tab for `tabRetentionMs` and an act waits up to `reconnectGraceMs` for the page to come back.

**[S-RELAY-5] Which tab.** Each agent acts on one tab at a time: the one it chose with `relay_select-tab`, else the most recently active connected tab of its person, which is then kept for that agent until it chooses another, so a tab becoming active never moves an agent between its observe and its act.

**[S-RELAY-6] Revisions across tabs and reloads.** The revision the relay presents is the tab's revision plus an offset: a random base per tab record, and a further offset per page instance, so that the revisions presented for a tab never decrease across reloads and a revision read before a reload, or from another tab, never equals a revision it is checked against. `expectedRev` is translated back before the act reaches the page. Ledger sequence numbers the relay presents continue across reloads the same way; the page's own ledger begins again with the page.

**[S-RELAY-7] The record.** The page records every act the relay forwards with the actor `<principal> (agent via relay)`, whatever the agent sends. A refusal the relay's runtime makes before the page on an action call (the stale check, a schema failure) is recorded by the bridge ([S-AXE-14]) and forwarded to the page, which appends it under the same actor with `source: "server"`, so the page's ledger has no gap. A decision the person makes outside the page ([S-RELAY-12]) is appended to the page's ledger as `op: "approve"` or `op: "deny"` on the entry, with an actor naming the principal and where they decided (`<principal> (approved in the agent's MCP client)`, `<principal> (approved on the relay's approval page)`). A refusal that never reaches a connected page (a stopped or disconnected tab, a pending or denied approval) is not in the page's ledger; the relay reports it in the tool result, and its own connection events (`onEvent`) record connections, refusals, Stop, and pairing.

**[S-RELAY-8] What crosses the wire.** The page sends the relay what `observe()` and `ledger()` return, so [S-PRV-1] and [S-PRV-2] apply before anything is sent: a sensitive field's value is never in a frame. The application's `objects`, the tab's title, and its path (never its query) do cross. Text on the page reaches the agent as data, under protocol §18.

**[S-RELAY-9] The person approves consequential acts: in the page when attended, in the agent's UI when unattended.** By default an act on an action whose effect is `risk: "high"` or declares `confirm`, or that the surface itself holds with a `handoff` whose reason is `approval_required` (an auto-derived gate), does not run on its first request: the page holds it under an approval id and returns `unavailable` with `details.reason: "approval_required"` and a sentence for the agent to say to the person. Where the person decides is the page's choice, `approvals` on `connectRelay`: `page` (the default when attended) shows the request with the control's name in the page; `agent` (the default when unattended) has the relay ask through the calling agent's MCP client ([S-RELAY-12]); `both` does either, and the first decision holds. A decision in the page grants the relay's gate and the surface's own gate together. After the person approves, the next request with the same entry, op, text, `confirm`, and `expectedRev` runs once; a denied one is `forbidden` with `details.reason: "approval_denied"`; an open request lapses (default five minutes). `requireApproval` changes which rows need approval. The indicator that shows an agent is connected, Stop, and the approvals is on by default; an application that turns it off MUST render its own with Stop and the approvals. None of these controls is registered on the surface, so no agent reaches them through the relay. In unattended mode the indicator is off by default and Stop comes from the agent's side ([S-RELAY-13]).

**[S-RELAY-10] Development pairing.** `devPairing` is for local development only. The relay MUST refuse to listen on an interface other than loopback, and MUST refuse a request whose peer is not a loopback address or whose `Host` is not a loopback name. It serves development tokens (`POST /dev/token`) to the allowed origins, accepts agents over HTTP only with its development key (or over stdio), and gives each connected tab a pairing code, shown in the indicator, that an agent presents with `relay_pair`; five wrong codes lock an agent out for a minute.

**[S-RELAY-11] Injected connection.** A host that opens the application in a hidden browser session for a person (`@summationai/axe-host`) MAY set the global `window.__AXE_RELAY__` to `{ url, token, mode, indicator? }` before any page script runs, where `token` is a relay token for that person and `mode` is `unattended` or `attended`. `injectedRelay()` MUST read it only when called, never at import, and return `connectRelay` options (with `indicator` off unless the global says otherwise, for `unattended`), or null when the global is absent or malformed. `relayOptions(fallback)` returns those options when present, keeping the fallback's other options but none of its endpoint, token, mode, approval channel, or indicator, and the fallback otherwise. An injected connection needs no pairing: the relay authenticates the token as any other ([S-RELAY-2]), and an agent reaches the tab only through its own verified identity ([S-RELAY-3]). The tab reports its mode and approval channel in its first message, and `relay_tabs` lists the mode.

**[S-RELAY-12] Approvals through the agent.** For a tab whose approval channel is `agent` or `both`, when the tab holds an act for approval during an agent's tool call, the relay MUST ask the person through MCP elicitation on that tool call (the same session, related to the same request) where the client and transport allow it, and MUST NOT take a decision from anything the model sends (a tool argument, `confirm`, text). It uses form mode, a single boolean confirm whose message names the control, the application, what the act changes and its risk, and the act's text unless the entry is sensitive, when the client declared form mode and the act is not sensitive. It uses URL mode with a page the relay serves (`/approve/<id>`) when the act is sensitive (a sensitive entry, or `approvals.sensitive`) or the client declared URL mode only, and only when the page's origin is `https` (or `http` on loopback) and the relay can establish who opens it (`approvals.identify`, or loopback in development). The page MUST refuse anyone but the approval's principal and tenant, a link used once already, a link past its lifetime (default five minutes), a decision without the nonce from the page it served, and a cross-origin post, and MUST NOT be framed; `accept` on the URL elicitation means the person agreed to open the page, and the relay waits for the page's decision. Otherwise (no elicitation declared, a stateless exchange, or the client failing to show the request) the tool result is the `approval_required` refusal, saying why, with `details.approvalUrl` when the relay serves approval pages. On a decision the relay sends the tab `approve` or `deny` with the approval id; the tab MUST accept it only for its own open approval and only when its channel is `agent` or `both`, grants its gates exactly as a decision in the page does, records it ([S-RELAY-7]), and the relay sends the act again, which the page decides as any act: an approval runs the bound request once, and decline or dismissal is `forbidden` with `details.reason: "approval_denied"`. A tool call cancelled while the person decides runs nothing; the decision stays with the tab for an identical retry.

**[S-RELAY-13] Stop from the agent's side.** `relay_stop` ends agent access to one of the caller's tabs (its current tab, or a `tabId` from `relay_tabs`) as Stop in the page does ([S-RELAY-4]): the token is revoked, the tab is marked stopped, and the page is closed with the Stop code, so a host closes its hidden session. `relay.stop(who, tabId?)` does the same for the relay's owner (a host's own control). In unattended mode a person stops a session by asking the agent, through the host's own control, or by revoking the agent's authorization, after which it reaches no tab ([S-RELAY-3]). The relay's `onEvent` records who stopped a tab.

**[S-RELAY-14] An act the page does not answer.** An act can leave the page before it settles: its click navigates (a link, a form that posts and reloads), or the page closes or crashes. When the unload began as a navigation (`beforeunload`, then `pagehide`, while the act runs), the tab MUST answer the act before it closes its connection, as `ok` with `navigated: true`, `changed: []`, and a notice telling the agent to observe the new page; it records the act in its ledger. Otherwise the relay MUST report an act it forwarded and did not get an answer for (the connection closed, or `actTimeoutMs` passed) as `unavailable` with `retryable: false` and `details.reason: "outcome_unknown"` (`details.cause`: `tab_disconnected` or `tab_timeout`), saying the act was sent and may have taken effect. Neither answer says nothing was applied, and neither is retried by the SDK; the AXE runtime stores an `outcome_unknown` error under the call's idempotency key ([P-OP-3]), so a retry with the same key is answered with it and does not run the act again.

### 9.2 Unattended sessions

Unattended is the SDK's default mode for an agent outside the browser: the person signs in once, in the agent's own UI (MCP OAuth), and never has to open the site. `@summationai/axe-host` (`createHost`, `axe host`) runs the application in a headless browser for the principal and tenant the agent's sign-in names, the application's own page (with the `SurfaceProvider` that `axe surface init` mounted) connects its surface to the relay, and the agent acts through the relay's tools (§9.1) on that page. Attended mode (the person's own tab, with pairing in development) remains the fallback. The rules below are what the host guarantees.

**[S-HOST-1] One session is one identity.** A hosted session is for exactly one principal in one tenant: the one the agent's verified access token names (`agentAuth.identify` over HTTP), or the identity a stdio or development host was started for. The host MUST mint the page's relay token for that identity and no other, and MUST resolve every tool call to the session of its caller's identity only; the relay's [S-RELAY-3] applies on top, so an agent reaches no other person's tab by any tab id.

**[S-HOST-2] Isolation.** Each identity gets its own browser context: cookies, storage, cache, and permissions are never shared between two identities, and a different tenant for the same principal is a different session. Contexts share only the browser process.

**[S-HOST-3] No pairing.** The host MUST inject the relay connection ([S-RELAY-11]) before any page script runs, as `window.__AXE_RELAY__` with `mode: "unattended"` and `indicator: false`, and only into frames whose origin is the application's; the page's renewal function (`getToken`) MUST mint only for such frames and only for the session's identity. No pairing code is issued and `relay_pair` is not offered. Relay tokens are short-lived (`tokenTtlSeconds`, default ten minutes) and renewed in-band ([S-RELAY-4]).

**[S-HOST-4] The application issues its session.** The application session a hosted browser starts with comes from `sessionFor`, which the application supplies; the SDK never issues one. What `sessionFor` returns (cookies, headers, a storage state, `localStorage`) MUST NOT be logged, put in an event, or returned by any tool; headers go only to the application's origin. A `sessionFor` that returns null or throws starts nothing, and the agent is told `unavailable` with `details.reason: "host_session_unavailable"` without the error's text, except for the explicit `SessionLoginRequired` handoff in [S-HOST-9].

**[S-HOST-5] Everything through the page.** An agent changes nothing but through the hosted page's surface ([S-RELAY-1]): the host adds no tool that changes application state, and `host_screenshot` only reads the page as it is.

**[S-HOST-6] Approvals through the agent.** Nobody sees a hosted page, so nothing is approved in it: a hosted page takes approvals through the agent's MCP client ([S-RELAY-12]), and an act that needs approval does not run when the client cannot ask the person.

**[S-HOST-7] Navigation stays on the application.** A navigation (top-level or in a frame) to an origin other than the application's and `allowedOrigins` MUST be refused, leaving the page where it was; `restrict: "all"` refuses every request to such an origin. Cloud metadata endpoints are never reachable, and service workers, which would fetch around these rules, are blocked. Each refusal is an event naming the origin, never the full URL.

**[S-HOST-8] Lifecycle.** A session starts on its identity's first tool call and is ready when its page's surface is connected to the relay. A session with no tool call for `idleMs` (default fifteen minutes) is closed; past `maxSessions` the least recently used is closed; a crashed or closed page is started again on the next call under the same relay tab id. The agent's `relay_stop` closes the session, and a later call may start another; Stop by the person or the owner (`stop`, the development watch page) closes it and starts none for that identity until `resume`. In development (`dev`, `axe host --dev`) the host MUST listen on loopback only and refuse a request whose peer or `Host` is not loopback, and `/mcp` takes only the development key or stdio.

**[S-HOST-9] Brokered application login is a human handoff.** A `sessionFor` may throw `SessionLoginRequired` with an HTTP(S) application login URL, safe instructions, and an expiry. The host MUST start no browser session, MUST return `needs_human` with reason `application_login_required`, and MUST expose no password or other credential. Its opaque resume token and stored original request MUST expire, MUST be bound to the verified principal and tenant, and MUST be invalidated by owner Stop. `axe_resume` MUST call `sessionFor` again; while login is incomplete it returns a retryable conflict and runs nothing, and after the application supplies a session it replays the exact original request. A duplicate resume MUST return the stored result without running the request twice.

**[S-HOST-10] A signed-out hosted page has a session-bound human form.** When the connected Surface reports `profile.authentication.state: "signed-out"`, the host MUST pause the original agent request and MAY return `needs_human` with reason `application_login_required` and a short-lived HTTPS URL (loopback HTTP in development). That URL MUST operate on the exact browser page and context already bound to the caller's principal and tenant; it MUST NOT copy credentials, cookies, storage, or relay tokens into MCP, Surface, a URL, a log, or another browser context. A generic fallback MAY present safe labels and standard visible HTML fields and actions as a provider-owned form, but MUST NOT return their values, page screenshots, or arbitrary page HTML to that form. Each submission MUST be bound to the current document and form revision, accepted only at the unguessable URL from its own origin, applied only to the identified fields and action, and never offered as an agent tool; a stale revision MUST be refused. Polls MUST NOT race older state over newer state, and a transient read failure or a DOM remount with unchanged field semantics MUST NOT be reported as expiry, discard entered values, or appear as a new step. A password-visibility control MUST remain an auxiliary, value-preserving field control rather than becoming the form's primary action. A primary action that appears only after an input event MAY be re-read and invoked only while the field semantics remain unchanged; this behavior MUST use standard form semantics rather than application-specific selectors or labels. While the handoff page is actively polling, another application call SHOULD report the pending handoff without presenting another URL. The generic fallback MUST NOT collect credentials after navigation away from the application's origin. Navigation remains subject to [S-HOST-7]. The link and stored request expire and are invalidated by Stop. `axe_resume` MUST run nothing until a fresh Surface observation reports `signed-in`, then replay the exact stored request once; it MAY wait a bounded interval after a recorded form submission for that state to settle, and duplicate resume returns the stored result. Completion MUST remain observable from the already-open page and MUST be visually distinct from an expired or ended session. The application needs no handoff route or session broker for this fallback: it reports only its live authentication state through Surface.

## 10. Derived surfaces and configuration

Declaring every control is the most exact surface and the most work. `@summationai/axe-surface/auto` starts from the other end: it reads what the page already tells assistive technology (roles, accessible names, disabled states and their descriptions, values, the dialogs, landmarks, and headings a control sits in) and registers one entry per control on an ordinary surface. That is the base layer. A configuration overlay adds what the page cannot say, and entries the application registers itself stand beside both. Everything in §2 to §9 applies to derived entries unchanged; this section says what is derived, what it guarantees, and what it does not.

**[S-AUTO-1] Three guarantee tiers.** Every entry carries its tier as `tier` (absent means declared), and `observe()` reports `tier` on every entry that is not declared. `tier` is not the ledger's `source` ([S-LED-8]), which says where a ledger entry came from.

| Tier        | Where it comes from                                                                             | What an act runs                                              | What it guarantees                                                                                                                     |
| ----------- | ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `derived`   | The page's accessibility semantics, read by `autoSurface`.                                      | The events a person's click or typing causes on that element. | The same outcome a person would get from that control at that moment, nothing more. The name, the reason, and the risk are heuristics. |
| `annotated` | Derived, then refined by a configuration rule or by `data-surface-*` attributes on the element. | The same events.                                              | As derived, with names, objects, reasons, and effects a person reviewed in the configuration.                                          |
| `declared`  | `register`, `useSurface`, the configuration's `declare`, or a rule's `handler`.                 | The application's own function.                               | Everything §3 to §6 state, including conditional writes ([S-ACT-11]).                                                                  |

A derived act cannot carry the revision into the application's write: the page's events have no place for `expectedRev`. Its staleness check is the surface's own ([S-AUTO-6]); a server-side conditional write needs the declared tier.

**[S-AUTO-2] What becomes an entry.** Actions: `button`, `a[href]`, `summary`, and the roles `button`, `link`, `menuitem`, `menuitemcheckbox`, `menuitemradio`, `tab`, `switch`, `checkbox`, `radio`, `option`, `treeitem`, and a `combobox` that is not a text input (a list trigger). Fields: `input` (not `hidden`, `file`, or a button type), `select`, `textarea`, and a contenteditable host. Collections: `grid`, `treegrid`, `table`, `listbox`, `tree`, and a `list` or `feed` only when it can load more. Landmarks (`main`, `navigation`, `search`, `complementary`, and a named `region` or `form`) become targets of `navigate` unless the configuration sets `landmarks: false`. An element hidden from everyone (`hidden`, `display: none`, `visibility: hidden`, a closed `<details>`, or, with layout, no box) is left out by default; `hidden: "unavailable"` lists it as unavailable instead. A control without an accessible name is left out and reported as a gap ([S-AUTO-10]). An entry the application registered under the same id, including one whose control carries its `data-surface-id`, wins: the scan never replaces it. The scan reads open shadow roots and same-origin frames; a closed shadow root and a cross-origin frame are not read, and are reported.

**[S-AUTO-3] Names and keys.** The name is the accessible name, computed in the order of the accessible name algorithm: `aria-labelledby`, `aria-label`, the native label (`label[for]`, a wrapping `label`, `alt`, a button's `value`, `legend`, `caption`), text content for roles named from content, `title`, then `placeholder` (and a rich-text editor's `data-placeholder`); for a field with none of these, short text just before it; for an icon-only control, the icon's class or sprite name; for a link, its path's last segment. Each name records where it came from and a confidence: high for a label or text, medium for `alt`, `title`, a button value, a heading, or a landmark role, low for a placeholder, nearby text, an icon, an `href`, or a single glyph. The object is the innermost named container: a table row's label, a list item's or article's nearest heading, a dialog, a menu or group, a region named by `aria-label` or `aria-labelledby`, a named landmark, else the nearest heading before the control.

The id of a derived entry is its key: `<route>#<containers>/<role>:<name>`, where the route is the path with numeric, UUID, and long hexadecimal segments replaced by `:id`, the containers are the landmarks and named containers from the outside in, and each part is lowercased with runs of other characters turned into `-`. Two controls with the same key in one context get `~2`, `~3` in document order; two links with the same key and destination are one entry. A `data-surface-id` on the element, or a rule's `id`, replaces the key. Keys survive a re-render that recreates the nodes, attribute and class changes, and a sibling inserted anywhere except between exact duplicates. They change when the visible name changes (a count in the label, another language), when the row label or heading changes, when a landmark is added around the control, and, for duplicates, when one is inserted before another. A pin (`data-surface-id` or a rule's `id`) is the fix for each.

**[S-AUTO-4] Acting by the same door.** An act on a derived action brings the element into view and dispatches, in order: `pointerover`, `pointerenter`, `mouseover`, `pointerdown`, `mousedown`, focus (unless `mousedown` was cancelled), `pointerup`, `mouseup`, and `click()`, which runs the element's activation behavior (a checkbox toggles, a link follows, a submit button submits). A field is focused and its value set through the element's native setter, so a framework that tracks the value (React) sees a change, followed by `input` and `change`; a `select` chooses the option whose label or value is the text and publishes its choices as the field's `schema` so an unknown option is `invalid_input`; a contenteditable host has its contents selected, then receives `beforeinput` with `inputType: "insertText"`, then, unless that was cancelled, `execCommand("insertText")`, then direct text with `input` as a last resort. A collection loads more by its load-more control when it has one, else by scrolling its scroller by about a screen and firing `scroll`. An act whose element is no longer on the page is `conflict`: nothing is dispatched on another element.

**[S-AUTO-5] Settling and notices.** After dispatching, the act waits for a microtask, an animation frame (bounded), and a quiet period with no DOM change (`observe.settle.quietMs`, default 50 ms, bounded by `timeoutMs`, default 1500 ms), then re-scans, and reports as `changed` every entry that was added, changed, or removed while it ran. Text that appeared during the act in a live region, an alert or status, a toast, or a new top-level element that is not a dialog or menu is reported as `notices` in the act's output (`HandlerReport.notices`, at most five). Changes after the settle move the revision later; the act reports the page as it stood when it settled.

**[S-AUTO-6] Revision and staleness.** The scan follows the root, every open shadow root it read, and every same-origin frame with a `MutationObserver`, and `input`, `change`, `toggle`, `reset`, `popstate`, and `hashchange` events; changes are coalesced (`observe.debounceMs`, default 30 ms). A re-scan moves the revision (`bump`) exactly when an entry was added, removed, or changed in what `observe()` reports (name, state, value, effect, availability); a DOM change that alters no entry leaves it. `observe()` and `act()` on the surface first apply any change the observer has not delivered yet, so an act presenting the revision of a page that has since changed is refused as `conflict` ([S-ACT-2]), and the act queue and its checks apply unchanged ([S-ACT-9]). With `revision: "none"` the surface's revision stays the application's.

**[S-AUTO-7] Risk heuristics.** Every derived action gets an `effect` from its role, words, styling, and surroundings. Changing what is shown (a tab, a tree item, an option, a disclosure, a menu or panel trigger, a checkbox or radio in a form, a row selection, a link within the site) is `low` or `none`, reversible. A link that leaves the site is `medium`. A submit, a save, or another commit word in the verb position is `medium`. A destructive word anywhere in the name (delete, remove, archive, revoke, disconnect, cancel subscription, reset, purge, drop, overwrite, send, publish, pay, purchase, invite, transfer, share, sign out, and the rest of the lexicon), a destructive style (a `danger` or `destructive` class, `data-variant="destructive"`, a red button), a control that opens an `alertdialog`, or the affirmative button of a confirmation dialog is `high`. A switch, or a checkbox or radio outside a form, is `medium`. A control named for an item among its peers is `low`, reversible, and changes `location`: it sits in an item of a list, table, menu, or grid, or is (or sits in) an item block among sibling blocks of the same shape (a block holding a heading, other controls, or at least two separate pieces of text: a card, a row of columns), allowing for up to three levels of wrappers; it is outside a toolbar; and most of its peers' counterparts have names of their own (an organization, a tenant, a table; two folders may share a name). A name repeated across the items is an action done to each of them and is not an item. A filter strip is `low` and changes `view`: at least three sibling controls of the same element and class, most with names of their own, and most either naming a count ("Snowflake (7)") or carrying `aria-pressed`, `aria-selected`, or `aria-current`. Rules above apply first, so a destructive name or style among items stays `high`; for a control that is itself an item block, whose name is the item's data, a destructive word counts only at the start of the name (`refund_events` is a table, not a refund). Words are whole words, and `_` joins a word. A menu, listbox, or tree that a control opened (named by that control's `aria-controls` or `aria-owns`, or naming a popup trigger in its `aria-labelledby`) belongs to that control's dialog wherever it is rendered, so a portaled menu of a modal is neither behind the modal nor outside its staged choice. A control none of this recognizes is `high`, and coverage says so. Word lists are English by default and extend or replace through the configuration's `lexicon`.

**[S-AUTO-8] Policy.** What an agent may do at each risk level is the configuration's `policy`: `allow`, `approve`, or `deny`; the default allows `none`, `low`, and `medium` and requires approval for `high`. An entry that needs approval is unavailable with the reason "needs the person's approval (…)" and a handoff with `reason: "approval_required"`, no `url`, and a sentence for the agent to say to the person ([S-AV-3]); it is reported in the act's refusal and in the bridge's `availability`. `handle.approve(id, { uses, ttlMs })` records the person's approval of one entry for a number of acts (default one) within a time (default five minutes); it MUST be called only from the person's own interaction in the page, never from anything an agent can reach. `deny` makes the entry unavailable with a reason and no handoff. A rule's `approval: true` or `false` overrides the policy for its matches.

**[S-AUTO-9] Privacy.** A password field, a field whose `autocomplete` is a card field (`cc-*`), `one-time-code`, `current-password`, or `new-password`, a field matching the configuration's `sensitive` selectors, and a field a rule marks `sensitive` are sensitive ([S-PRV-1]): no value in `observe()`, the ledger, or coverage, and read only to agents unless a rule sets `editable: true`.

**[S-AUTO-10] Coverage.** `handle.coverage()` returns, for the page now: counts by kind, tier, and name confidence; every entry with its key, name source and confidence, risk and why, policy, and a CSS selector; the entries that wait on the approval policy; the gaps (unnamed controls, icon-only controls, weak names, duplicate names, likely duplicates of declared entries, clickable elements with no role, canvas and SVG charts and other opaque regions, naming the library when it can tell, cross-origin frames, virtualized collections with only their rendered rows, file inputs, closed shadow roots, controls whose effect was not recognized); the content an agent cannot read (charts and canvases drawn as graphics, closed shadow roots, cross-origin frames), each with its title and a selector, as `unreadable` ([S-AUTO-14]); the configuration rules that matched nothing; problems with the configuration itself; and, for each gap it can close, a configuration rule to paste and edit. `formatCoverage` renders it as Markdown. With `expose`, `window.__surface` carries `coverage()`, `formatCoverage()`, and `refresh()` beside the members of [S-DOM-2]. Coverage is a report, not a score: its purpose is the next edit to the page or the configuration.

**[S-AUTO-11] Generic tools.** A derived surface is served through a fixed set of parameterized actions rather than one per control ([S-AXE-10]): `autoActions(handle)` in `@summationai/axe-surface/axe` is `domainActions` over `autoDomains()`, which is one action per configured group, then `navigate` (a link within the site, a landmark, or the `navigate` entry, which takes a same-origin path as its text and opens it through a link on the page with that path, the configured `navigate` function, `history`, or a full load), `set-field`, `run-control` (declared `high`, so every control fits), and `load-more`. The tool list is the same size whatever the page renders. Declared entries may still be served one action per control through `surfaceActions`.

**[S-AUTO-12] Lifecycle.** `autoSurface()` runs in the browser after the page exists; nothing in `@summationai/axe-surface`, `@summationai/axe-surface/auto`, or `@summationai/axe-surface/react` touches `document` or `window` at import. `stop()` disconnects every observer and listener, ends every pending wait with `met: false` ([S-AUTO-15]), unregisters every derived, annotated, and configured entry (never one the application registered), and restores the surface's own `observe` and `act`. `SurfaceProvider` and `useAutoSurface` (`@summationai/axe-surface/react`) start it in an effect on mount (so a server render derives nothing), register on the module-level `surface` by default so declared and derived entries share one table, re-scan after pushState, replaceState, `popstate`, and when a router location passed as `location` changes, reconfigure when `config` changes identity, publish `window.__surface` with `expose`, start nothing when `flag` (or `enabled`) is false, and stop on unmount.

**[S-AUTO-13] What is not derived.** The scan does not see: a framework handler on an element with no role (reported, and promoted by a rule with `selector` and `role`), text drawn on a canvas, a chart without an accessible name or data, a cross-origin frame, rows a virtualized list has not rendered, a closed shadow root, a value an element keeps outside the DOM, and CSS generated content. Coverage reports each it can detect.

**[S-AUTO-14] Reading the page.** `handle.read({ region, query, maxChars, maxRows, cursor })` returns the content the page renders for the person, and nothing it does not: `{ route, path, title, rev, region?, sections, notices, truncated, nextCursor?, redacted, reason?, regions? }`, where each section is `{ heading, level, text, fields, tables, lists, opaque?, truncated? }`. Sections follow the headings (`h1` to `h6`, `role="heading"` with `aria-level`) in document order, content before the first heading forming a section of level 0; a dialog, a named region (`aria-label`, or `aria-labelledby` naming something other than its own heading), a sectioning element, and a card whose first child is styled or classed as a title each scope a section, so content after them returns to the enclosing one. Fields are label and value pairs from `dt`/`dd`, a two-column table of row headers, an element named by `aria-labelledby` or described by `aria-describedby`, two short leaves one of which is marked as a label, a line of the form "Label: value" outside a document's prose, a progress bar or meter, and the page's form controls (a select by its chosen labels, a checkbox as checked or not, the chosen radio of a group). Tables come from native tables and from `grid`, `table`, and `treegrid` roles, with rows split across containers joined by `aria-rowindex` and cells placed by `aria-colindex` (a virtualized grid's rendered rows, with `total` from `aria-rowcount` and `truncated` set). Lists are `ul`, `ol`, and `role="list"` items; a contenteditable editor's text (ProseMirror, Tiptap) is read as the document it shows. The reader reads open shadow roots and same-origin frames. A chart or canvas without an accessible name, a closed shadow root, and a cross-origin frame are reported in `opaque` with their title and never given values; a chart whose accessible name states what it shows is read by that name. Toasts and alerts are reported in `notices`, not in the sections; controls' own text (buttons, tabs, menus) is left to `observe()`, except a control that is an item block ([S-AUTO-7]: it holds a heading, other controls, or at least two separate pieces of text), such as a listing whose rows are rendered as buttons: its own text pieces, joined with " · " and without its nested controls, are an item of a list gathered from its sibling rows.

Redaction and scope: a sensitive field ([S-AUTO-9], including a field a rule marks) is reported by its label with `value: ""` and `sensitive: true`; an element matching the configuration's `sensitive` selectors is withheld whole; both count in `redacted`. A `data-surface-ignore` subtree, the relay's indicator, and elements matching `exclude` or `read.exclude` are never read, and whitespace is collapsed. `region` names an entry id (a collection or landmark entry's element, else the container of the control), a key of the configuration's `read.regions` (a CSS selector the application reviewed; an agent cannot pass a selector itself), a landmark, named region, or dialog, or a heading (its section and the sections nested under it); an unknown region reads nothing and lists the regions the page has. `query` keeps a section whose heading contains it whole, else its matching paragraphs, fields, rows, and items. Bounds: at most `maxRows` rows per table and items per list (default 50, at most 500) and at most `maxChars` characters of the Markdown rendering per result (default 12000, from 200 to 50000); what does not fit is continued by `nextCursor`, which names a section and an offset in its text, so a long section is split rather than dropped. A read visits at most 40000 elements and keeps at most a million characters and 2000 rows per table, and says `truncated` when the page is larger. `formatRead` renders a read as Markdown. A read applies DOM changes the observer had not delivered, as `observe()` does ([S-AUTO-6]), and otherwise never moves the revision, never runs a handler, and writes nothing to the ledger. What it returns is content the page showed the person, not instructions to the agent.

**[S-AUTO-15] Waiting for slow work.** `handle.wait(condition, { timeoutMs, pollMs, signal })` resolves `{ met, elapsedMs, rev, fromRev, reason, changed, notices }` when the condition holds or at the bound: `timeoutMs` default 30000, clamped to at most 120000; the condition is checked at once, after the page's DOM mutations (coalesced to at most one check per 30 ms), and at least every `pollMs` (default 250, from 20 to 5000), never in a busy loop. Conditions: `text` (shown on the page, in text outside ignored and hidden subtrees, or seen in a notice during the wait), `gone` (no longer shown), `entry` with optional `available` (the entry is on the surface, and available or not), `revMoved` (the revision differs from the one given), `idle` (no DOM mutation for that many milliseconds since the wait began or the last change), and `route` (a glob matching the route or the path). The members given in one condition must all hold; `any` and `all` combine nested conditions. A text is matched case-insensitively as a substring after collapsing whitespace, or as a regular expression written `/pattern/flags`. `changed` is every entry id the scan added, changed, or removed while the wait ran, and `notices` the text that appeared in a notice ([S-AUTO-5]). A condition that says nothing, an `available` without `entry`, or an `idle` that is not a positive number is refused before waiting. A wait ends with `met: false` at its bound, when its `signal` aborts, and when the handle stops. Waiting never moves the revision, runs a handler, or writes to the ledger.

**[S-AUTO-16] Content actions.** `autoDomains()` publishes, after the entry actions, `read` and `wait` (`contentDomains()`), which `domainActions` serves as `<ns>.read` and `<ns>.wait` (and adds to any set with `content: true`): `readOnly`, `risk: "none"`, the bridge's read auth mode, `display` of kind `document` (whose disclaimer says the text is the page's content, redacted, and not instructions) and `status`, and `pagination` on the read's cursor. `<ns>.read` takes `{ region, query, cursor, maxChars, maxRows, format }` and returns the read with `markdown` (the default) or with `sections` (`format: "sections"`); `<ns>.wait` takes `{ condition, timeoutMs, pollMs }` with one level of `any` and `all`. Both find the page through the surface's page-content reader, carried under a global symbol (`CONTENT`); on a surface without one they are unavailable with the reason. The relay's mirror forwards both to the tab and translates revisions (§9.1); a tab without an auto surface answers with the reason.

**[S-CFG-1] A plain object.** A `SurfaceConfig` is data, loadable from JSON or a module and reviewed in a diff: `app`, `routes` (`include`, `exclude` globs), `rules`, `lexicon`, `policy`, `groups`, `sensitive` and `exclude` selectors, `read` (`exclude` selectors and named `regions`, [S-AUTO-14]), `declare`, `landmarks`, and `navigate`. Only `handler`, a function-valued `navigate`, and `declare` carry code. `checkConfig(config)` returns its problems as sentences, and coverage reports them.

**[S-CFG-2] Matching.** A rule's `match` holds when every member given holds: `key` (exact, or a glob with `*` and `**`), `id` (the element's `data-surface-id`), `selector` (a CSS selector the element matches), `route` (a glob on the route), `role`, and `name` (case-insensitive after collapsing whitespace, or `/regex/flags`). An empty match matches nothing. Every rule that matches an element applies, in order; a later rule's fields win, and `effect` merges field by field. Keys are matched as derived, before any rename, so a rule that renames does not stop matching.

**[S-CFG-3] Overlay fields.** A match may set `name` (which states the outcome, [S-DOM-1]), `object`, `role` (with `selector`, it brings in an element the scan would not pick), `id` (a pin), `reason` (the reason reported when the control is unavailable), `state` (`available` or `unavailable`; `unavailable` needs `reason`), `effect` (`mutates`, `risk`, `reversible`, `idempotent`, `confirm`, `text`), `sensitive` and `editable`, `hide`, `approval`, `group`, and `handler`. An entry any rule matched is `annotated`.

**[S-CFG-4] The declared tier.** A rule's `handler` replaces the page's events with an application function; it receives the entry id, the element (when it is on the page), the act's text, the actor, the presented `expectedRev`, and `dispatch()`, which runs the derived act when the handler wants both. Its entry is `declared`. It MAY report `changed`, `rev`, `conflict`, and `notices` as any handler does ([S-ACT-1], [S-ACT-11]).

**[S-CFG-5] Raising and lowering risk.** A rule's `effect.risk` replaces the heuristic's; the policy then decides from the configured risk. Lowering a control's risk is a reviewed statement that it is safe for an agent; coverage lists every high-risk entry so the review has the list in front of it.

**[S-CFG-6] Groups.** `groups` declares domain actions (`title`, `description`, and the highest `risk`, `reversible`, and `idempotent` that hold for every member), named with lowercase letters, digits, and hyphens; a rule's `group` folds its matches into one. `autoActions` publishes each group before the defaults, so a group's members act through it.

**[S-CFG-7] Stale configuration.** A rule that matched no control is reported in `staleConfig`: `stale` when its `route` matches the page and it matched nothing here (the control was renamed, moved, or removed), `unmatched` when it has no `route` and has matched nothing on any page seen so far.

**[S-CFG-8] Iteration.** `handle.configure(config)` replaces the configuration and re-scans; the revision moves if any entry changed. Declared entries of the previous configuration are unregistered and those of the new one registered. A bridge made by `autoActions` keeps the groups it was made with.

## Provenance

[S-AUTO-14] to [S-AUTO-16] came from the product's target demo: a person asks an agent in Claude for the status of a project in the application and then for a generated report, and the agent drives the real application through its derived surface. A surface described controls only, so the agent could press "Generate report" but could not say what the page said, and had nothing to hold on to while the report took a minute to appear. The reader's fallbacks (card titles, label and value leaves, ARIA grids joined by row index inside open shadow roots, editors read as documents, charts named but never read) are the first target's facts: no landmarks, table cards in open shadow roots, Tiptap editors, Highcharts with accessibility off, a canvas spreadsheet, virtualized ag-grid rows, toasts that are not live regions.

v0.9 came from an agent demoing the Plan Board (`docs/examples/demo/plan-board.ts`) over MCP, which reported two gaps in the ledger: no entry for the revision the person's "Approve March" moved (the approval changed state and bumped the revision outside `act`), and no entry for its own first February edit, refused as stale by the server before the surface (the protocol's first gate, [S-AXE-4]), while `<ns>.ledger` described itself as holding every refused act. [S-LED-8] and [S-AXE-14] close both, and [S-LED-1] says what the ledger holds.
§9.1 and the new [S-MODE-3] came from the product's integration path, in which an agent (Claude Code over MCP) drives a signed-in person's live tab: the rule that the SDK carries nothing between a page and a server made that impossible, so the broker is now the SDK's own, stated with its guarantees. The design uses the existing bridge rather than a second mapping to tools: the relay's mirror implements the surface interface `domainActions` reads. Its limits (in-memory, one process, an approval gate a page script could press) are in `docs/relay.md`.

v0.9 came from the product question of what installation alone should give an application: most of a correct surface, read from the page it already renders for people and assistive technology, with the rest supplied by a reviewed configuration. The coordinator's study of the first target application (React 19 with server rendering, an open shadow root around table cards, rich-text editors with no accessible name, icon-only links in a collapsed sidebar, no landmarks, toasts that are not live regions, charts and a spreadsheet drawn opaquely, a virtualized grid) set the fixtures; running the scan over the documentation site and the reference application found the rest (a verb-position rule for view and commit words, one entry per link destination, the nearest heading as context).

v0.7 came from the same review's item on existing agent interfaces (`docs/review/2026-09-24/14-agent-interface-adapters.md`): WebMCP gives the browser's agent a tool API of its own, and a surface already has everything a tool needs (names, reasons, schemas, a guarded act).

v0.7 came from the review's item on execution modes (`docs/review/2026-09-24/13-execution-modes.md`): a React hook registers closures in a browser, and importing the same module in a Next route shares none of that registry, session, or state. The reference application (`examples/plan-review`) serves its domain actions from the server and keeps its page controls in the page, and its tests show both, and the absence of anything between them.

[S-ACT-6] to [S-ACT-8], [S-REV-5], and the rules of §5.2 came from two defects found on a real planning application in the first staging trial, both in the seam between Surface and the application: an act whose `target` was `null` matched a row that was not actionable, and the table kept reporting cells editable while the application had frozen editing during a save, so an act ran into the frozen UI. Both were fixed in the application and became rules of the contract here, so the next application does not find them again.

v0.6 came from the same review's item on mounted React behavior (`docs/review/2026-09-24/11-react-lifecycle.md`). Mounted tests under jsdom showed that `useSurface` kept the old id registered after an id change and removed the wrong one at unmount, registered nothing in a new target surface, and ran the handler from the render that last changed `deps`; and that `useSurfaceProps` never heard a registration made outside the component, because registration did not notify. Ordering under ordinary updates, Strict Mode without an id change, freezes, and the removal of a stale reason already held.

v0.5 came from the engineering review of 2026-09-24, which found every generated action inheriting `auth: "none"` and a server configured with `none` and `user` modes serving observe, the ledger (with typed text), and every mutation to an anonymous caller (`docs/review/2026-09-24/05-surface-authorization.md`).

v0.4 came from integrating the SDK into that application rather than porting it: a browser bundle that failed on a Node built-in and carried Zod for a schema it never used ([S-ENT-3]); freezes that moved a revision the server owned ([S-FRZ-2], [S-FRZ-3]); `changed` that was always empty and a ledger whose `revAfter` never moved, because the revision arrived after the handler ([S-ACT-1], [S-LED-5]); a DOM mirror that said editable while `observe()` said frozen, and could not clear a stale reason ([S-DOM-1]); a collection with nothing to load published as an action that could never run ([S-AXE-6]); a human-only step with no page to point at, reportable only as a bare reason ([S-AV-3], [S-AXE-2]); and over-length text refused in front of the surface, so the attempt never reached the ledger ([S-LED-1]). Each was first shimmed in the application; each is now the contract.

v0.5 came from a review that ran two asynchronous acts presenting the same `expectedRev` against one surface: both passed the check, both ran, and both returned `ok`, because the check ran before the handler and nothing held the revision while the handler awaited. A preflight comparison is not concurrency control, and the `app` revision mode did not change that. The surface now orders its own acts and checks a waiting act again at execution ([S-ACT-9], [S-ACT-10]); across instances, where no local queue can help, the handler gets the presented revision for its conditional write and a way to say it failed ([S-ACT-11]); and a handler's late answer can no longer roll the revision back ([S-REV-6]).
